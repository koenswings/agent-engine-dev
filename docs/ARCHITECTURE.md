# Technical Architecture

Based on the source code and documentation, here is a technical architecture summary of the Powerberries project.

### **1. Core Concept: Physical Web App Management**
The project implements a distributed "Physical Web App Management" system. Instead of installing software on a central server, web applications are contained on portable physical drives (**App Disks**). When these disks are docked into a Raspberry Pi-based appliance (**Appdocker** or "Engine"), the system automatically detects, mounts, and executes the apps contained within them.

*   **Appdocker (Engine):** A Raspberry Pi device running the custom "Engine" software.
*   **App Disk:** An SSD or USB stick formatted with `ext4` containing Docker Compose definitions and data for web apps.
*   **Clients:** Devices on the same network that access the apps via a web browser.

---

### **2. Software Architecture: The "Engine"**
The core software is a Node.js application called the **Engine**, managed by `pm2` for persistence and auto-restart. The architecture relies on a local-first, distributed state model using **Automerge** to synchronize data between devices without a central server.

#### **A. State Management (Automerge Repo)**
The project moved away from Yjs/Valtio (referenced in brainstorming notes) to **Automerge** for conflict-free data synchronization.

*   **The Store:** The central data structure is a single shared Automerge CRDT document containing maps for Engines, Disks, Apps, and Instances. Every Engine on the network maintains its own local copy of this document and continuously merges it with copies from its peers. The result is that **every Engine holds a complete, up-to-date view of the entire network** — which engines exist, which disks are inserted into which engine, and which app instances are running where — without any central coordinator.
*   **Initialization (The "Golden Template"):** To solve the "offline-first" initialization problem (where two offline nodes create diverging documents that can never be merged), the code implements a specific pattern found in `repo.ts` and `Store.ts`.
    *   The system uses a binary template file (`store-template.json`) containing an empty store document, and one shared document ID: the fleet store URL in the tracked `store-identity/store-url.txt` (the same value as `FLEET_STORE_URL` in `src/data/StoreIdentity.ts`).
    *   **Store identity at startup (idea#120):** `prepareStoreIdentity` runs before the store is opened. If `store-url.txt` is missing, it is written back atomically (temp file + rename) with `FLEET_STORE_URL`. An existing `store-url.txt` is used as it is, whatever it contains (an isolated Engine such as idea03 deliberately uses its own store ID); it is never corrected. `store-template.json` is never created or written by the Engine: if it is missing, startup stops with an error telling you to restore it from git. `store-url.txt` is read only when needed (`readStoreDocId`), never at module load. The old `initialiseServerStore`, which created a random store and overwrote the template, is gone.
    *   **Command log at startup (idea#145):** `createCommandLogStore` loads the doc named in `store-identity/command-log-url.txt` with a timeout (`findCommandLogWithTimeout`, `COMMAND_LOG_LOAD_TIMEOUT_MS` = 10 s). On a fresh Engine the tracked URL points at the fleet's shared command log, which no peer may have (a new school Pi has no peers), and after a `store-data` wipe the Engine's own previous log is gone from storage; `repo.find()`/`whenReady()` used to wait forever there and the Console never came up. If the doc is unavailable, the URL is empty or invalid, or the timeout passes, the pending find is aborted, a fresh CommandLogStore is created and its URL is written to `command-log-url.txt` (the tracked file then differs from git on that Engine). The command log is ephemeral history, so nothing needed is lost; the main store and its sharing are not affected. The unavailable handle stays in the Repo's cache, so shutdown uses `shutdownRepo`, which falls back to flushing only the ready documents when `repo.shutdown()` fails on it. Tests: `test/automated/fresh-engine-start.test.ts`.
    *   **System `/META.yaml` at startup (idea#145):** the Engine id comes from `/META.yaml` (`localEngineId` in `Engine.ts`, read at import). If the file is missing (a freshly flashed Pi that never ran `build-engine --personalize`), `readMetaUpdateId` first calls `ensureSystemMeta`, which writes one with `sudo tee /META.yaml` (10-engine): diskId from the root disk's hardware serial when `readHardwareId` finds one, otherwise a generated id; `diskName` = diskId; the Engine version from `package.json`. In testMode/isDev nothing is written and the Engine stops with an error that says how to fix it (as it does when the write fails); `getLocalEngineId` prints that reason before exiting instead of a bare crash.
    *   On startup, the Engine attempts to load the main document from local storage. If it does not exist (first boot), it imports this binary template. This ensures all nodes start with the **same document ID**, allowing them to merge seamlessly when they eventually connect — even if each has been operating independently for days.
*   **Storage:** Data is persisted to the local filesystem using `NodeFSStorageAdapter`. Each Engine's local copy survives reboots and is incrementally merged with peers on reconnection.

#### **B. Data Flow: Monitors & The Repo**
The application uses a "Monitor" pattern. Monitors listen for system events (USB insertion, network changes, time) and update the Automerge Repo. The Repo then syncs these changes to other peers.

*   **USB Device Monitor (`usbDeviceMonitor.ts`):**
    *   Watches the `/dev/engine` directory for new storage devices. The udev rule `90-docking.rules` creates symlinks there for three device patterns:
        *   `sd?` — whole-disk device (no partition table; e.g. `sda`)
        *   `sd?1` — first partition (single-partition disks; e.g. `sda1`)
        *   `sd?2` — second partition (dual-partition disks; e.g. `sda2`)
    *   **Symlinks are not followed (idea#110):** the watcher runs with chokidar `followSymlinks: false` (`DEVICE_WATCH_OPTIONS` / `watchDeviceFolder`). It only sees links being added to and removed from `/dev/engine`; it never watches the `/dev/sd*` block devices behind them, which are `root:disk 0660` and unreadable for `pi` (following them gave `EACCES` watcher errors). Mounting goes through sudo, so the Engine never opens the block device. `pi` is deliberately not in the `disk` group (that would grant raw read access to every drive).
    *   **Detection health (idea#82):** `boot.sh` reinstalls the udev rule on every boot when it is missing or differs from the shipped asset, then reloads and re-triggers udev. At startup the Engine runs a read-only self-check (`diskDetection.ts`: rule present and matching, `/dev/engine` present, a `/dev/engine/<name>` entry for every `sd?`/`sd?1`/`sd?2` in `/sys/class/block`, after `udevadm settle` and one delayed re-check). Self-check problems and monitor start, watcher, mount, META read, META write, dock and undock failures are written to the command log as failed traces with command `diskDetection` (args `{ step, device, ... }`), so they appear in Console History without a store schema change.
    *   When a disk is inserted, it mounts the drive, reads its `META.yaml` identity, and scans for App instances.
    *   **Safe mount and unmount (idea#126, Files Disk step 0, `src/monitors/mounts.ts`):**
        *   *Already mounted?* Before mounting, `checkMountState()` reads the mount table with `findmnt -J -l -o SOURCE,TARGET,FSTYPE` and looks at the **target** (`<disksRoot>/<device>`) **and the source** (`/dev/<device>`), for every filesystem type. The old check searched `mount -t ext4` output, so after an Engine restart a docked **vfat** partition was mounted a second time on top of itself (Atlas, idea03). This device already at its target (also a stacked mount) → no new mount. Another filesystem at the target, or `mountpoint -q` says the target is a mount point → **refused**. This device mounted somewhere else → refused. A refusal is a failed `diskDetection` trace (step `mount`) and the disk is not registered.
        *   *fsUuid:* after a mount (or when the existing mount is found) the filesystem UUID is read with `lsblk -no UUID /dev/<device>` (no sudo) and kept in memory for `Disk.unmountError`.
        *   *Undock:* the store is updated first (disk undocked), the disk's instances are stopped (their containers keep files on the disk open), then `unmountAndRemove()` runs `sudo umount <mountPoint>` again and again until `mountpoint -q <mountPoint>` is false (each umount removes one layer of a stacked mount), and then removes the empty folder with exactly `sudo /usr/bin/rmdir /disks/<device>` (`/etc/sudoers.d/11-engine-files`; a plain rmdir under test roots). Never `rm -fr`: rmdir fails on a folder that is not empty, so a still-mounted disk's data can never be deleted.
        *   *Retry count:* `UMOUNT_MAX_ATTEMPTS = 5` umount calls per undock, with `UMOUNT_RETRY_DELAY_MS = 1000` (1 s) after each failed call. Rationale: a successful umount also counts as an attempt, so 5 covers the double mount seen on idea03 (2 calls) plus three busy retries, about 3 s of waiting for a process that is just letting go of the disk (a stopping container, a finishing rsync). A holder that is still there after that will not go away by itself; waiting longer would only block the undock and the Console, and the operator is told to restart the Pi instead.
        *   *Busy unmount:* if the mount point is still mounted after the retries, nothing is removed, a failed `diskDetection` trace (step `undock`, args `{ device, diskId, mountPoint, fsUuid }`) is written, and `Disk.unmountError = { engineId, mountPoint, fsUuid, message }` is set, for every disk type (App, Backup, empty, later Files). `mountPoint` is stored because `device` is `null` after undock. The error is kept after undock and cleared by the next successful mount (`createOrUpdateDisk`). The Console warns on that Engine's row and the disk's view ("Restart this Pi").
        *   *Startup cleanup:* `start.ts` calls `clearStaleUnmountErrors()` before the monitors start. For every `unmountError` with this Engine's `engineId` it runs `findmnt -no UUID <mountPoint>`: nothing mounted → cleared; another UUID than `fsUuid` (device names get reused) → cleared; the same UUID → kept; `fsUuid` unknown and something still mounted → kept. Errors of other Engines are never touched.
        *   *Stale mount points at startup:* folders in `<disksRoot>` of devices that are no longer attached are removed with the same rmdir when they are not mount points (by `findmnt` target and `mountpoint -q`); mounted ones are left alone. (Before, they were moved to `/disks/old`.)
        *   Tests: `test/automated/mount-safety.test.ts` (fake `MountOps` through `setMountOps`, and fake `findmnt`/`mountpoint`/`lsblk`/`sudo` binaries for the exact arguments). In testMode the real mount commands are skipped unless a test injects `MountOps` (`mountCommandsActive()`).
    *   **First dock writes META.yaml (idea#121):** when a disk has no `META.yaml`, the monitor builds its identity (diskId from the hardware serial when `readHardwareId` finds one, otherwise a random UUID; name from the volume label via `lsblk -no LABEL`, otherwise `Unnamed Disk`) and writes it to `<disksRoot>/<device>/META.yaml` with `writeMetaFile()` from `Meta.ts`. The mount roots under `/disks` are root:root, so for `/disks/sd[a-z][12]/META.yaml` it runs `sudo /usr/bin/tee <path> > /dev/null` with the YAML on stdin, allowed by `/etc/sudoers.d/11-engine-files`; under any other disks root (test and fixture roots) it writes the file as pi. Every later dock reads the same diskId back, so the disk keeps one `diskDB` entry. If the write fails (read-only mount, sudoers entry missing), the monitor records a failed `diskDetection` trace with step `writeMeta` and still registers the disk. The write is skipped when `skipMetaWrite()` in `Config.ts` is true: `settings.skipMetaWrite` if set, otherwise `testMode` (like `readMetaUpdateId`). `test/automated/meta-first-dock.test.ts` runs the real write. Entries left behind before this fix (a new random id per dock) are removed with `script/cleanup-store.ts --orphans-only` (see docs/SCRIPTS.md).
    *   **META identity flags (idea#168):** `readMetaUpdateId` reads the hardware serial unless `skipHardwareId()` and rewrites an existing META.yaml (lastDocked, a changed diskId, the older-format upgrade) unless `skipMetaUpdate()`; a missing system `/META.yaml` is created only when `allowSystemMetaCreate()` (= `!skipMetaUpdate()`). Both are `settings.skipHardwareId` / `settings.skipMetaUpdate` when set (env `IDEA_SKIP_HARDWARE_ID` / `IDEA_SKIP_META_UPDATE` = `true|false`), otherwise `isDev || testMode` — the old gate. Under fixture mounts (pi-owned `IDEA_DISKS_ROOT`, devices like `idea-test-N`) the lookup finds no `/sys/block` entry, so a META without `isHardwareId: true` keeps its id, and the rewrite is a plain write as pi (`writeMetaFile`). `skipMetaWrite` (the first write on a disk without META.yaml) is separate. Tests: `test/automated/meta-identity-flags.test.ts`. The serial reader is picked by `hardwareIdReaderFor(model, vendor)`: model `Flash Drive FIT` → `scsi_id`, vendor `INTENSO` in any case (idea01 reports `Intenso`) → `sudo hdparm -I` (`test/automated/meta-hardware-id.test.ts`).
    *   It updates the `Disk` and `Instance` objects in the Automerge Store.
    *   **One record per device (idea#152):** a device holds one disk, but a stale `diskDB` record can still claim it (e.g. left by an undock from before idea#126, whose failed unmount returned before the store was updated; undock now updates the store first). `createOrUpdateDisk` undocks, in the store only, every other record on the same engine+device when a disk docks (`clearDuplicateDiskRecords` in `Disk.ts`). Device removal undocks every record on the device (`undockAllOnDevice`, using `findDisksByDevice` in `Store.ts`). At startup, when several records share a device that is still attached, the one whose id matches the device's `META.yaml` is kept and the others are undocked (`resolveDuplicateDisksOnDevice`); without a match, the dock of the device resolves them. `ejectDisk <diskId>` resolves by disk id through the shared resolver (`resolveDiskArg`, below); a name still works but only matches records docked to this engine with a device, and two such records are refused as ambiguous. Eject also undocks any stale record on the same device, then unmounts through the idea#126 path (umount loop, `sudo rmdir`, `unmountError`). Every refusal (not found, not docked, other engine, ambiguous, locked, running backup) throws, so the `ejectDisk` trace ends as `error` with the reason.
    *   **The system disk is never ejected (idea#152):** the root partition's record (`System Disk`, e.g. sda2) gets `diskTypes: ['system']` as soon as it is registered, before `/apps` and `/instances` are scanned. That value is the marker the Console gates its eject button on (`!diskTypes.includes('system')`). `ejectDiskWrapper` refuses the system disk by id or by name, and `undockDisk` never undocks it (`isSystemDiskRecord` in `Disk.ts`: the marker, or a device on the drive that holds `/`, i.e. the root partition or the boot partition on `/boot/firmware`). Before this, an `ejectDisk` on it undocked the record (device null, row gone) and would have stopped its instances; `/` itself stayed mounted because the unmount only looks at `/disks/<device>`.
    *   It triggers the execution of apps (via Docker).
    *   **Offline service images (idea#81):** Starting an instance first loads each service image with `docker image load` from the App Disk's `services/<image with / → _>.tar` (`serviceImageTarPath()` in `Instance.ts`; the same path is used when an instance is built). No network is needed. If a tar is missing or `docker image load` fails, the start does not stop (idea#109): the problem is logged and added as a `warn` log line to the start's `startInstance` History entry, and `docker compose create/up` pull the image if it is not local and the Engine has internet (production allows pulls; only test fixtures set `pull_policy: never`). The start fails only if create or up fails. The load is skipped only when `skipImageLoad()` is true: `settings.skipImageLoad` if set, otherwise `testMode`. `test/automated/service-image-tar-load.test.ts` runs the real load in every `test:full`.
    *   **Docker available, not testMode (idea#168):** the Docker metrics poll (`pollDockerMetricsOnce`), the `startInstance` "containers already running" shortcut and the container logs in `diagnoseInstance` run when `dockerAvailable()` (`src/utils/dockerAvailable.ts`) is true: `settings.dockerAvailable` (env `IDEA_DOCKER_AVAILABLE=true|false`) when set, else a cached `docker info` probe (an answer is kept 10 min, no answer 60 s; concurrent callers share one probe). They used to be skipped in testMode, which the duration pool runs with real Docker. Tests: `test/automated/docker-available.test.ts`.
    *   **Start status (idea#109):** `startInstance` sets an instance to `Running` only after `docker compose up -d` has succeeded (`runInstance`), so the Console never shows Running for containers that did not start. `createInstanceContainers` (`compose create`) and `runInstance` (`compose up`) throw on failure; `startInstance` catches every failure (port, image load, create, up), sets `Error` with a diagnosis in `statusCondition`, marks the `startApp` operation `Failed`, and records a failed `startInstance` trace in the command log (`recordInstanceStartFailure`), so it shows in the instance's Console History. When the start runs inside a `startInstance` trace (the Console command or the dock auto-start) that trace is closed as `error`; otherwise (post-copy, post-move, backup-post-start) a completed failed trace with args `{ instanceName, instanceId, diskId, cause }` is added. `closeTrace` never turns an `error` trace back into `ok`. Start warnings (an image that could not be loaded from its tar) are `logs` entries with `level: 'warn'` in the same entry; a start that succeeds with warnings outside a `startInstance` trace gets a completed `ok` trace holding them.
    *   **No `.env` values in logs (idea#111):** an instance's `.env` holds its app password (`pass`, generated by `startInstance`) and other app secrets, and History is readable from the Console. The Engine logs `.env` variable names only, never values (`readEnvVariable`, `addOrUpdateEnvVariable`, the pass step of `startInstance`, and `uuid()`, which is not logged because it generates the pass). The Engine-assigned `port` is the exception: it is also in the store and shown in the Console. A `config.yaml` parse error is logged as its first line only, because the YAML parser quotes file lines (which can include `defaults.password`). `test/automated/no-env-values-in-logs.test.ts` checks that a real start's History entry has no `.env` value.
    *   **Generated ids and app passwords (idea#114):** `uuid()` in `src/utils/utils.ts` makes disk, instance and operation ids and the app password `startInstance` writes to an instance's `.env` (`pass`). It draws 19 characters from `[0-9a-z]` with Node's `crypto.randomInt` (`secureRandomString`, no modulo bias), about 98 bits, instead of `Math.random` plus a timestamp. Existing passwords and ids are kept; only new ones use the new generator. `Math.random` is left only where the value is not a secret (random port candidates, hostname generation, test-runner peer ids).
    *   **Disk type detection:** Disk type is determined at runtime by inspecting the filesystem content of the mounted drive. A disk may be multiple types simultaneously. `processDisk` runs all detection checks and populates `diskTypes: DiskType[]` on the `Disk` store entry. `DiskType = 'app' | 'backup' | 'empty' | 'upgrade' | 'files'`. Detection functions in `Disk.ts`: `isFilesDisk` (checks for `FILES.yaml`, idea#131), `isAppDisk` (checks for `apps/` directory), `isBackupDisk` (checks for `BACKUP.yaml`). `isUpgradeDisk` remains a stub. **Processing order (idea#131, Files Disk R5):** Files first, then App, Backup and Upgrade, so an App on the same disk sees the Files role before its instances start; `diskTypes` is still stored in the fixed order `app, backup, upgrade, files`. A Files-role error (for example an unreadable `FILES.yaml`) is recorded as a failed `diskDetection` trace with step `files` and does not stop App or Backup processing; the disk keeps `'files'` with `filesConfig: null`.
    *   **Files Disk (idea#131, Files Disk step 1):** identified by `FILES.yaml` in the disk root (`version`, `created`, `createdBy`, `shareName`, `readOnly` (reserved, ignored), `password` (reserved, must be null)); the shared content is `files/`. `processFilesDisk` (`src/data/FilesDisk.ts`) sets `Disk.filesConfig: { shareName, readOnly, passwordProtected, error }`, or `null`; `error` is only used for a password-protected disk ("password-protected Files Disks are not supported yet"; such a disk is never mounted into Apps). The password never goes into the store. A missing `shareName` falls back to the disk name. `filesConfig` is reset in `createOrUpdateDisk`, `undockDisk` and `clearDuplicateDiskRecords`, like `backupConfig`. The role combines with App and Backup (`['app', 'files']`, `['app', 'backup', 'files']`). It is added with `createFilesDisk` (`src/data/CreateFilesDisk.ts`, see COMMANDS.md), the only code that changes a disk root's owner (`sudo /usr/bin/chown -h pi:pi /disks/<device>`, `11-engine-files`, only when `pi` can't write the root; previous uid:gid and mode in the trace first). Mounting `files/` into opted-in Apps is **idea#133 (step 2)** (`src/data/FilesMount.ts`): `x-app.filesMount: { path, services }` is stored as `App.filesMount`. Each Files Disk appears at `<path>/<slug>-<id6>` (slug from `shareName`, always suffixed with the first six characters of the disk ID); display names travel as a read-only bind of `.idea-files.json`. A per-instance compose override (long bind syntax, `bind.create_host_path: false`) lives under `~/.local/state/idea-engine/files-overrides/`; every `docker compose` create/up for an opted-in instance sets `COMPOSE_FILE=compose.yaml:<override>`. Status table: Running → `up -d`; Stopped left alone; Pauzed/Docked → `up --no-start --force-recreate`. `Instance.filesMounts` is written only after a successful compose up. **Grouping window (open Q2):** runtime Files Disk docks coalesce over `FILES_REMOUNT_GROUP_MS` = **3 seconds**. **Hold-back (open Q1, Kid):** recreate is held while `Instance.status === 'Starting'`, while a Running/Pending `startApp`/`stopApp`/`upgradeApp` Operation (or the matching instance lock) targets the instance, and — for Nextcloud (`nextcloud-app`) when Running — until `docker exec <id>-nextcloud-app-1 runuser --user www-data -- php occ status --output=json` reports `installed: true`, `maintenance: false`, `needsDbUpgrade: false` (fail closed on missing occ / non-zero / bad JSON). Held remounts are queued and retried. Same-disk instances are skipped on Files dock (they start once via `processAppDisk` with the override already containing that disk's `files/`); on undock/eject, other-disk opted-in instances are remounted without the bind before same-disk instances are stopped and the disk is unmounted once. Password-protected Files Disks are never mounted. `files/` on a Backup + Files disk is not backed up. **Erase (idea#134, step 3):** `summariseDisk` / `eraseDisk` erase any non-system disk to an empty IDEA disk (`['empty']`, label "IDEA Disk", only `META.yaml`, `root_owner=1000:1000`). Mount only with `/usr/bin/mount -t ext4 …` (11-engine-files). System drives via `findmnt` `/` + `/boot/firmware` and `lsblk -no PKNAME` (`SystemDisk.ts`). `Engine.unformattedDisks` lists whole non-system disks without ext4. `idea-erase-disk` (copy in `/usr/local/sbin`) re-checks serial/size/system/mount/swap; no role-marker refusal; `wipefs -a` exit trap; staging under `~/.local/state/idea-engine/erase-staging/<id>/` holds only META.yaml. Capability `eraseDisk`.
    *   **Disk size (idea#131):** every docked disk gets `Disk.sizeBytes` and `Disk.freeBytes` (free space available to `pi`), read with `fs.statfs` on the mount point (`/` for the system disk; no sudo) at the end of `processDisk` and every 10 minutes (`enableDiskSizeMonitor`, `src/data/DiskSize.ts`). Values are rounded to whole MB and written only when the size changes or free space moves by more than 1% of the size or more than 100 MB. Both are set to `null` on undock (`undockDisk`, `clearDuplicateDiskRecords`).
    *   **Backup Disk:** Identified by `BACKUP.yaml` in the disk root. `processBackupDisk` (in `backupMonitor.ts`) reads the config, sets `backupConfig: { mode, links }` on the `Disk` store entry, scans for stale lock files (boot-resume), and triggers `backupInstance` for `mode: immediate`. Backups use BorgBackup (`borg create`). **Locks (idea#126):** every backup takes the instance lock and the Backup Disk lock together with `resourceLock.acquireAll([instance:<id>, disk:<backupDiskId>])` (`backupLockKeysFor`), as restore does, and releases both when it ends; if either is held, the backup is not started and its trace ends as `error` with the reason. A failure inside a backup marks the `backupApp` operation `Failed` and ends its trace as `error` with the message (a Console `backupApp` command's trace included); monitor-started backups (immediate mode, stale lock, App Disk docked) log the failure and go on with the next one. `ejectDisk` refuses a disk while a `backupApp` operation with that `backupDiskId` is `Pending` or `Running` (`runningBackupOnDisk`), whatever started it. There is no erase command in the Engine yet; it must use the same check. `createFilesDisk` uses it too (idea#131). A `.backup-in-progress` lock file is written before each backup and removed on success; stale locks trigger re-backup on next dock. `Instance.lastBackup: Timestamp | null` is set in the store after each successful backup. **`skipBorg` (idea#168 r36@98):** `backupInstance` (`borg init`, `borg create`) and `restoreApp` (`borg info` + `borg extract`) skip borg when `skipBorg()` in `Config.ts` is true: `settings.skipBorg` if set (env `IDEA_SKIP_BORG=true|false` overrides it at load), otherwise `testMode`, like `skipImageLoad` and `skipMetaWrite`. testMode alone used to skip borg, so on a pool that runs testMode for its fixture disks a backup ended `Done` with no Borg repository and `restoreApp` refused "No docked Backup Disk with archives"; such a pool sets `skipBorg: false`. borg runs as root through the app-data helper (`borg-init`, `borg-create`, `borg-info`, `borg-extract`, idea#168, see below). Tests: `test/automated/skip-borg.test.ts` (fake `sudo` on PATH).
    *   **App version tracking:** When a disk is docked, the Engine reads the `version` field from the instance's `compose.yaml` (`x-app.version`) and stores it as `instanceOf` in the store (e.g. `'kolibri-1.1'`). If the disk has been re-prepared with a newer version since its last dock, `instanceOf` is updated automatically and the instance restarts with the new version. `lastStarted` is refreshed in the store.
    *   **App data as root: `idea-app-data` (idea#168):** containers write instance data as root (Kolibri sessions, 0600), 999 (MariaDB, 0700 folders) and www-data (Nextcloud, 0640/0770). The Engine runs as pi, so instance DATA is sized, copied, sent, deleted, backed up and restored by one root helper, `/usr/local/sbin/idea-app-data` (`script/build_image_assets/idea-app-data`, Bash, installed by build-engine `installUdev` as a root-owned 0755 copy), run with `sudo -n` and allowed by ONE line with no argument list in `11-engine-files` (`pi ALL=(root) NOPASSWD: /usr/local/sbin/idea-app-data`). The Engine side is `src/utils/appDataHelper.ts` (argv builders, `runAppData`, startup check) and `rsyncInstanceData` in `src/utils/rsync.ts`. Subcommands: `version`, `size <root> <id>` (du -sk -x), `copy <srcRoot> <srcId> <dstRoot> <dstId>`, `send <srcRoot> <srcId> <host> <dstRoot> <dstId>` (rsync over `runuser -u pi -- ssh` to `pi@<address>`, where `sudo -n idea-app-data receive <dstRoot> <dstId>` hands the stream to `rrsync -wo <dst>`), `delete <root> <id>` (rm -rf --one-file-system; a missing folder is fine), `borg-init|borg-info <bdev> <id>`, `borg-create <bdev> <id> <archive> <srcRoot>`, `borg-extract <bdev> <id> <archive> <strip> <dstRoot>` (extracts into a fresh root-only staging folder on the target disk, checks that only `<id>` came out, then moves it into place, replacing a previous folder of that instance). rsync runs with `-aHAX --numeric-ids -x`; borg with `--numeric-ids` and `BORG_RELOCATED_REPO_ACCESS_IS_OK=yes`, `BORG_UNKNOWN_UNENCRYPTED_REPO_ACCESS_IS_OK=yes` (repositories become root-owned). **Arguments are tokens, never paths:** a root is `system` (`/instances/<id>`), `sdX1`/`sdX2` (must be mounted at `/disks/<dev>` from `/dev/<dev>`, ext4, not on the system drive, with `META.yaml`; Backup Disks also need `BACKUP.yaml`) or, only through the bridge below, a test slot name; ids match `^[a-z0-9][a-z0-9-]{0,63}$`; archives match the names `backupInstance` makes. The helper checks exact argument counts, resolves every folder with `realpath -e` (no symlink anywhere in the path), refuses source data with a symlink that leaves the instance folder (copy and send), refuses a destination that exists and is not empty, uses absolute binary paths, a fixed `PATH`, `umask 022` and `LC_ALL=C`, takes per-instance / per-repository `flock`s under `/run/lock/idea-app-data`, and logs every call (caller, arguments, exit code, duration, refusal) with `logger -p auth.notice -t idea-app-data`. **send** only goes to private LAN and Tailscale addresses (10/8, 172.16/12, 192.168/16, 100.64/10): the helper resolves the host itself (`getent ahostsv4`), refuses if any address is outside those ranges, loopback, or nothing resolves, and connects to the checked address. **Cancel:** the Engine spawns sudo detached (its own process group, so sudo relays the SIGTERM `cancelOperation` sends); the helper stops rsync/borg and dies of the same signal. **TEST-ONLY root bridge `/etc/idea/app-data-roots`:** the duration pool's fixture disks are folders (`/home/pi/idea/duration-disks/<slot>`), not mounts. On a pool Pi only, this file lists absolute slot folders, one per line; a slot name (e.g. `idea-test-1`, never `sdX`/`system`) is accepted as a root only when the file is root:root, mode 0644, not a symlink, and the entry is absolute, has no `.`/`..` component, is a real folder with `META.yaml` and its parent folder is root-owned and not group/other writable. Otherwise the file or entry is ignored and the reason logged; every use is logged as `test-only root bridge`. Production never has this file; it is removed at Stage 2 (real USB disks on the pool). **Version check:** `start.ts` calls `assertAppDataHelper()` before anything else: unless `isDev`, the Engine refuses to start when `sudo -n idea-app-data version` fails or does not print `idea-app-data <APP_DATA_HELPER_VERSION>` ("… ask Ops to update the Engine's root helper …"). The version is a protocol number (bump it with the subcommands); install the helper and the sudoers line before deploying an Engine that needs them. App masters and service tars stay pi operations. Tests: `test/automated/idea-app-data-script.test.ts` (the script in a sandbox with fake rsync/rrsync/borg/findmnt/getent/logger, `test/harness/appDataSandbox.ts`), `test/automated/app-data-helper.test.ts` (Engine side, fake sudo).
    *   **Cross-disk upgrade detection (planned):** When a new App Disk is docked, the Engine will scan running instances for the same app name at a different version. If a newer minor-version disk is found alongside an older one, the Engine writes an upgrade proposal to the store. The Console reads this and presents it to the Console Admin, who can initiate the upgrade (data migration via rsync from old instance to new instance). Major version changes are not proposed — they are flagged as data-format incompatible and require explicit operator action outside the normal upgrade flow. See `App.ts`: `isMajorUpgrade()`, `extractMajorVersion()`.

*   **mDNS Monitor (`mdnsMonitor.ts`):**
    *   Uses the `ciao` library to advertise the local Engine's presence on the LAN via mDNS, so other Engines and Console UIs can find it without any configuration.
    *   Uses `node-dns-sd` to continuously scan for other Engines advertising the same service type.
    *   When a new peer Engine is discovered, it automatically initiates a WebSocket connection and begins Automerge sync. The two documents merge: each Engine now knows about the other's disks, apps, and instances. As more Engines appear on the network, this process repeats, progressively building a shared picture of everything available across all engines.

*   **Time Monitor (`timeMonitor.ts`):**
    *   Periodically updates the `lastRun` timestamp in the Engine object within the Store. This acts as a heartbeat, allowing the UI to detect if an Engine has gone offline.
    *   **Engine capabilities (idea#128):** at every startup `createOrUpdateEngine` (`Engine.ts`) writes `capabilities` (the whole list `ENGINE_CAPABILITIES`, currently `['diskIdArgs', 'filesDisk', 'filesMount', 'eraseDisk', 'instanceIdArgs']`; `filesDisk` = Files role + `createFilesDisk` (idea#131); `filesMount` = Files binds (idea#133); `eraseDisk` = summariseDisk + eraseDisk (idea#134); `instanceIdArgs` = start/run/stop/copy/move/backup/restore take an instance id (idea#168, `InstanceArg.ts`)) and `capabilitiesBootedAt` on the local Engine record `engineDB[engineId]`, from the same timestamp as `lastBooted`. The list is replaced, not merged, so a capability removed from the code disappears at the next boot. `capabilitiesBootedAt === lastBooted` tells a reader that the list was written by the Engine now running: after a rollback to an older Engine, `lastBooted` moves on but the old code leaves `capabilities` and `capabilitiesBootedAt` untouched, so they no longer match. The Console (agent-console-dev#126) sends disk ids only when `capabilities.includes('diskIdArgs') && capabilitiesBootedAt === lastBooted`.
    *   **Disk arguments (idea#128):** `installApp` (target and `--source`), `createBackupDisk` and `ejectDisk` resolve their disk argument with `resolveDiskArg(store, engineId, arg, command)` in `src/data/DiskArg.ts`: id first (must be docked to this engine with a device); otherwise a deprecated name fallback that only matches records docked to this engine with a device, refuses an ambiguous name and logs a `console.warn` deprecation line into the trace. Every refusal throws, so the trace ends as `error`. The system disk is resolvable (installApp may target it); `ejectDisk` refuses it separately.
    *   **pm2 `kill_timeout: 10000` (idea#128):** `pm2.config.cjs` gives the Engine 10 s after SIGINT before SIGKILL (pm2's default is 1.6 s), so shutdown can finish unmounting and flushing the store. pm2 only reads it when the process is (re)created from the config file.

*   **Store Monitor (`storeMonitor.ts`):**
    *   Listens for changes *coming from* the Automerge Repo — whether those changes originated locally (a disk was inserted) or were received from a remote peer (another engine updated its state, or a Console UI wrote a command).
    *   It reacts to these data changes to trigger side effects. Most importantly, this is how **remote commands work**: a Console UI writes a command object into the shared Automerge document; the document syncs to the target Engine; the Store Monitor on that Engine detects the new command entry and executes it locally (e.g. starting or stopping an app instance, ejecting a disk). The command channel is the shared document itself — no separate RPC layer is needed.

#### **C. Communication Topology**

The system forms a self-organising mesh on the local network with no configuration required.

*   **Engine ↔ Engine (peer sync):** Each Engine runs a WebSocket server (set up in `repo.ts`). When mDNS discovery finds a new Engine, a WebSocket connection is opened and Automerge sync begins. Changes flow in both directions and are merged automatically using CRDTs — no conflict resolution logic is needed. Once synced, every Engine's local document contains the aggregated state of all engines: every disk, every app instance, and every engine heartbeat visible on the network.

*   **Engine ↔ Console UI (read path):** A Console UI connects to any one Engine on the network via WebSocket. Because that Engine already holds the merged view of the whole network, the Console UI immediately receives the complete picture — all engines, all disks, all running apps — without needing to connect to each engine individually. The Automerge document is the single source of truth, and the Console UI subscribes to it like any other peer.

*   **Console UI → Engine (write / command path):** When a user performs an action in the Console UI (e.g. "start this app", "eject this disk"), the Console UI writes a command entry into its local copy of the Automerge document. That change syncs to the connected Engine, which syncs it further to the Engine that owns the relevant disk or instance. The Store Monitor on the target Engine detects the new command and executes it. The result (success, error, updated instance state) is written back into the document by the executing Engine and syncs back to the Console UI — closing the loop without any bespoke request/response protocol.

*   **Discovery:** All of the above is driven by mDNS on the local network. There is no central registry, no manual IP configuration, and no dependency on internet connectivity. Engines and consoles find each other automatically when they appear on the same subnet.
*   **Static peers (opt-in, idea#168):** Where mDNS is off, set `IDEA_STATIC_PEERS=host[:port],host[:port],...` (env var; or `settings.staticPeers` in `config.yaml`, same format, the env var wins). Each listed peer is dialled through the same `connectEngine` path as mDNS peers; the port defaults to the Engine's own peer port (`settings.port`, 4321). Hostnames are resolved to IPv4 first, so a peer also found by mDNS is not connected twice; this Engine itself is skipped; invalid entries are skipped with a warning. Failed attempts retry with backoff (5 s doubling to 5 min); a lost connection is redialled at the next 10 s check. Unset or empty: nothing changes. See `src/data/StaticPeers.ts`.

### **4. Summary of Data Flow**

#### Scenario A — Disk insertion propagates across the network

1.  **Event:** A user inserts a USB drive containing a "Kolibri" app into Engine A.
2.  **Detection:** `usbDeviceMonitor` on Engine A detects the hardware event.
3.  **Local Update:** The monitor writes a new `Disk` object and `Instance` object into the Automerge Store.
4.  **Execution:** Engine A reads the Docker Compose definition from the disk and starts the container.
5.  **Sync to peers:** The Automerge Repo propagates the change via WebSockets to all connected peers — Engine B, Engine C, and any connected Console UIs.
6.  **Visualisation:** Every Console UI observing the document immediately shows "Kolibri" as "Running on Engine A", even if the Console UI is physically connected to Engine B.

#### Scenario B — Console UI sends a command to a remote Engine

1.  **User action:** A user on a Console UI (connected to Engine B) taps "Stop Kolibri".
2.  **Command write:** The Console UI writes a command entry into its local Automerge document.
3.  **Sync:** The change propagates via WebSocket to Engine B, which syncs it further to Engine A (which owns the disk).
4.  **Execution:** The `storeMonitor` on Engine A detects the new command and stops the Docker container.
5.  **State update:** Engine A updates the `Instance` status to "Stopped" in the document.
6.  **Feedback:** The updated status syncs back through the mesh and the Console UI reflects the change — all without a dedicated RPC layer.

#### Scenario C — New Engine joins the network

1.  **Boot:** Engine C starts up for the first time and loads the golden template Store document.
2.  **Advertise:** `mdnsMonitor` advertises Engine C's presence via mDNS.
3.  **Discovery:** Engine A and Engine B detect the new advertisement and each open a WebSocket to Engine C.
4.  **Merge:** Automerge sync runs; Engine C's empty document merges with the full document from Engine A and B. Engine C now knows about all disks and instances on the network.
5.  **Visible to consoles:** Any Console UI immediately shows Engine C in its engine list, even before any disk is inserted into it.
