# Engine Command Reference

This document provides a reference for all commands available in the Engine's command-line interface.

---

## Inspection Commands

These commands are used to view the current state of the system. They can be run from any context.

### `ls`
- **Description:** A raw dump of all data in the shared store.
- **Usage:** `ls`
- **Scope:** `any`

### `engines`
- **Description:** Lists all engines discovered on the network.
- **Usage:** `engines`
- **Scope:** `any`

### `disks`
- **Description:** Lists all disks known to the network.
- **Usage:** `disks`
- **Scope:** `any`

### `apps`
- **Description:** Lists all applications known to the network.
- **Usage:** `apps`
- **Scope:** `any`

### `instances`
- **Description:** Lists all application instances known to the network.
- **Usage:** `instances`
- **Scope:** `any`

---

## Action Commands

These commands perform actions on the system. Some are restricted to an `engine` context, meaning they must either be run on an engine device directly or sent to an engine using the `send` command.

### `send`
- **Description:** Sends a command to be executed on a specific remote engine. This is the primary way to manage engines from a client.
- **Usage:** `send <engineId> <command> [args...]`
- **Scope:** `any`

### `installApp`
- **Description:** Installs an application onto a target disk. Routes to the appropriate source automatically:
  - `--source` given: copies the app bundle from a docked disk (works offline).
  - No `--source`, internet available: clones from GitHub (same as the old `createInstance`).
  - No `--source`, no internet: searches `appDB` for a locally known source disk; fails with a clear message if none found.
- **Usage:** `installApp <appId> <targetDiskId> [--source <sourceDiskId>] [--name <instanceName>] [--fresh]` (idea#128). The target and source are disk ids (the Console sends `disk.id`), resolved by the shared disk resolver (see [Disk arguments](#disk-arguments)). Both must be docked to this engine; a disk on another engine or an undocked record is refused (the old any-engine and undocked fallbacks are gone). Every refusal and usage error ends the command trace as `error` with the reason.
- **Scope:** `engine`
- **Examples:**
  - `installApp kolibri-1.0 f3a9c2d1` — auto-route (online → GitHub, offline → appDB lookup)
  - `installApp kolibri-1.0 f3a9c2d1 --source 7be04c11` — copy from a docked catalog disk
  - `installApp kolibri-1.0 f3a9c2d1 --source 7be04c11 --name school-kolibri` — custom instance name
  - `installApp kolibri-1.0 f3a9c2d1 --source 7be04c11 --name "Kolibri Demo" --fresh` — display name with a space, clean instance (idea#235)
- **Arguments are quote-aware:** the line is split with the shared `splitArgs` (see [Quoted arguments](#disk-arguments)), so a value with spaces goes in double quotes (`--name "Kolibri Demo"`). Lines without a `"` split exactly as before. An unexpected extra argument (e.g. an unquoted `--name Kolibri Demo`) is refused with the usage line.
- **`--name`:** the instance's display name. It is checked (not empty or blank, at most 64 characters, no control characters or newlines) and written to `x-app.instanceName` in the new instance's `compose.yaml` and to the store record, on both the GitHub route and the disk route. The instance id and folder, and so the Docker project, container and volume names, are still the generated id and never contain the name. Default: the appId.
- **App id forms:** `<name>-<version>` as stored on disks (`nextcloud-1.0-31.0.1`, `kolibri-channel-builder-2551b7d…`), or `<name>@<git ref>` for an exact repo ref that may contain `-` or `/` (`nextcloud@feat/nextcloud-demo`, `nextcloud@21d7f75`). A `<name>@<ref>` id is stored on disk as `<name>-<ref>`, with the ref made folder-safe (`/` becomes `-`). Parsing rules: `@` splits explicitly; otherwise the version starts at the first `-` followed by a digit; otherwise a trailing 7–40 hex commit SHA or `latest`; otherwise the last `-` (ambiguous, so use `@`). The GitHub route clones a branch or tag with `--branch`; a commit SHA is cloned and then checked out.
- **Same disk:** when `--source` is the target disk, the `apps/<appId>/` bundle is already in place and is not copied onto itself (paths compared with realpath).
- **`x-app.title`:** when the bundle omits `x-app.title` (or it is blank), the app record's title defaults to the app name so Automerge is not given `undefined` (idea#428). `createOrUpdateApp` and `processSystemApp` share this rule.
- **`--fresh`:** disk route only. The new instance starts from a copy of the whole app bundle (`apps/<appId>/`: compose.yaml, entrypoint scripts, hooks, bundled apps) with no data directory; no data is copied from an existing instance on the source disk. Without `--fresh` the disk route still copies the source disk's instance of the app when one exists. If there is no source instance, it copies the whole app bundle into the instance folder, the same as `--fresh` — not only `compose.yaml` and `.env` (idea#495; Nextcloud bind-mounts entrypoint scripts from the instance folder). Use `--fresh` for demo instances so they never inherit a school's data. The GitHub route always starts clean.

### `createInstance` *(deprecated)*
- **Description:** Deprecated alias for `installApp`. Use `installApp` instead. Builds a new application instance from a git repository.
- **Usage:** `createInstance <instanceName> <appName> <gitAccount> <gitTag> <diskName>`
- **Scope:** `engine`

### `startInstance`
- **Description:** Starts a previously created application instance. Before any Docker work, it re-reads `x-app` from the instance's `compose.yaml` and updates `instanceOf` (and the name / service images) through `createOrUpdateInstance`, so a manual `idea-app-data restore-snapshot` followed by `startInstance` shows the restored version in the store (idea#473). A legacy dotted instance id is refused with `Legacy instance id with a dot; remove it and reinstall` (no compose up, no `.env` rewrite, no port allocation); the store record is left listed as `Error` with that `statusCondition` so `removeInstance` can clear it (idea#494). This involves preloading services and creating and running the Docker containers. The instance becomes `Running` only after `docker compose up` succeeded and the instance host port has answered HTTP (any status line, including Nextcloud's 503 during maintenance or install) and stayed up for 10 seconds (idea#109, idea#437). A TCP accept alone is not enough: docker-proxy can accept connections before the app inside serves. The wait budget is `x-app.healthTimeout` (seconds) from the instance's `compose.yaml`; when that field is absent or invalid it is the per-App default that `updateApp` also uses (Kolibri 900 s, Nextcloud 300 s, others 600 s; one shared table, `src/data/AppHealthTimeout.ts`). The 10 s stable window, 1 s between probes and 2 s per-probe timeout are unchanged. If TCP itself never comes up within min(60 s, budget), the Engine force-recreates the containers once (r40) and keeps waiting only until the original budget ends — it does not start a second budget. It does not force-recreate when TCP is up but HTTP has not answered yet, so a long entrypoint is not killed. Any failure sets the instance to `Error` and closes the command's trace as failed. For an unpinned image, a missing or unloadable `services/<image>.tar` is only a warning (a `warn` log line in the trace): Docker pulls the image at create time if it can. For a digest-pinned image (idea#445), start skips the load when `repo@digest` is already local (and retags `repo:tag`); a tar whose digest does not match the pin is quarantined and never loaded, and start fails with a `stale service tar` error if the pin is not already local.
- **Usage:** `startInstance <instanceId|instanceName> <diskId|diskName> [--cause <cause>]` (idea#168). The instance resolves id-first (see [Instance arguments](#instance-arguments)); an ambiguous name is refused. `--cause` is sent by the cross-engine `copyApp` dispatch (`startInstance <newInstanceId> <targetDiskId> --cause cross-engine-cmd`). The trace arg keys stay `instanceName` and `diskId` (plus `options`).
- **Port:** the instance keeps the `port=` in its `.env` unless that port is listening (netstat), reserved (80, 8080) or owned by another instance in the store on this engine (idea#168 r35, `storePortOwner`); then, and when `.env` has no port, a fresh port is allocated that is none of those. When two records claim one port (data from before the fix), a Running/Starting claimant owns it, else the older record.
- **Second port, `port_zip` (agent-engine-dev#267):** only when the App's compose references `${port_zip}` or a default form such as `${port_zip:-8081}`. At each start the Engine keeps the `.env` `port_zip=` unless it is listening, reserved, equal to the instance's own `port`, or owned (as `port` or `port_zip`) by another instance in the store; otherwise, and when missing (an existing instance gets one at its next start), it allocates one with the same checks and writes it atomically to `.env` next to `port`. It is stored as `portZip` on the instance. Apps that don't reference it get nothing. For host-network Kolibri a literal `KOLIBRI_ZIP_CONTENT_PORT` is synced to it; a `${port_zip…}` reference is left for compose to resolve.
- **Scope:** `engine`

### `runInstance`
- **Description:** A shortcut for running an already-created instance's containers. Assumes `startInstance` has been run at least once. Sets `Running` only after `docker compose up` succeeded and the instance host port has answered HTTP for the same stable window as `startInstance` (idea#437); on failure the instance is set to `Error` and the command fails.
- **Usage:** `runInstance <instanceId|instanceName> <diskName>` (idea#168). The instance resolves id-first (see [Instance arguments](#instance-arguments)).
- **Scope:** `engine`

### `stopInstance`
- **Description:** Stops a running application instance and its associated Docker containers.
- **Usage:** `stopInstance <instanceId|instanceName> <diskId|diskName>` (idea#168). The instance resolves id-first (see [Instance arguments](#instance-arguments)); an ambiguous name is refused.
- **Scope:** `engine`

### `renameInstance`
- **Description:** Changes only an instance's display name (agent-engine-dev#220). It rewrites `x-app.instanceName` in `<disk>/instances/<id>/compose.yaml` (written as pi) and then `instance.name` in the store, so the name survives the next dock or Engine restart without a `pm2 restart`. The id, folder, Docker project, containers, volumes, data and port are unchanged. Nothing uses the display name as a key, so a running instance may be renamed.
- **Usage:** `renameInstance <instanceId|instanceName> <newName…>`. The new name is the rest of the line, quoted or not (`renameInstance kolibri-g3c6r "Kolibri Demo"`). An instance name must be unique among instances on this Engine (see [Instance arguments](#instance-arguments)); send the id.
- **Validation:** the name is trimmed, then must be 1–64 characters with no control characters (the same limits as `installApp --name`, `MAX_INSTANCE_NAME_LENGTH`), and unique, case-insensitive, among instances stored on this Engine. The same name as now is a no-op ok (`changed: false`, nothing written).
- **Result:** `CommandTrace.result` = `{ instanceId, oldName, newName, changed }`.
- **Refusals** (trace ends as `error`, `errorMessage` starts with the code): `NOT_FOUND`, `NOT_LOCAL` (stored on a disk not docked here), `AMBIGUOUS` (name shared on this Engine), `EMPTY_NAME`, `NAME_TOO_LONG`, `BAD_NAME`, `NAME_TAKEN`, `BUSY` (a copy, move, backup or restore holds the instance lock), `COMPOSE_WRITE_FAILED` (compose.yaml not written; store unchanged).
- **Capability:** `capabilities.includes('renameInstance') && capabilitiesBootedAt === lastBooted`
- **Scope:** `engine`

### `copyApp`
- **Description:** Refused with `NOT_DEMO` for a demo instance (engine#369; demo instances are not copied or moved).  Copies an app instance from one disk to another. The copy receives a brand new InstanceID — it is treated as a fresh instance. The original instance is stopped during the file copy (for a consistent snapshot) and restarted **before the copy starts**, so it keeps its port (idea#168 r35). Progress is tracked in `operationDB` in the store and visible to all Consoles.
- **The copy is its own instance (idea#168 r35):**
  - **Name:** `<name>-2`, or the next free `<name>-<n>` (n ≥ 2) that no instance in the store uses. Copying a copy continues its series (`kolibri-2` → `kolibri-3`, when `kolibri` exists); other names are kept whole (`kolibri-grade5a-001` → `kolibri-grade5a-001-2`). Written to the copy's `compose.yaml` `x-app.instanceName` (comments kept) and stored on the instance.
  - **Port:** the Engine-written `port=` and `port_zip=` lines are removed from the copy's `.env` (other lines are kept), so its start allocates a fresh port (and a fresh `port_zip` when the App uses it) (see `startInstance`). App keys such as `KOLIBRI_HTTP_PORT` in `.env` are not Engine-written and are left alone; the Engine rewrites the Kolibri listen env in `compose.yaml` to the allocated port at every start.
  - **Data:** refused when the instance folder holds a symlink that resolves outside it (see [Instance data links](#instance-data-links)).
- **Usage:** `copyApp <instanceId|instanceName> <sourceDiskId> <targetDiskId>`. The instance resolves id-first (see [Instance arguments](#instance-arguments)); a name shared by several instances resolves only to the one on the source disk. Crash recovery retries with the instance id. A cross-engine copy dispatches `startInstance <newInstanceId> <targetDiskId> --cause cross-engine-cmd` to the target Engine.
- **Scope:** `engine`

### `moveApp`
- **Description:** Refused with `NOT_DEMO` for a demo instance (engine#369).  Moves an app instance from one disk to another. The instance keeps its original InstanceID so backup disk links remain intact. The source instance directory (and app master, if no other instance on the source disk uses it) is removed after a successful transfer. After the copy has succeeded and before the instance is registered on the target, the source compose project is taken down with `docker compose -p <id> down` (never `-v`, so named volumes are kept) (idea#468). That order matters: the same instance id is the compose project name on both disks, so a down after start would stop the moved instance. If the instance was Running or Starting before the move, `moveApp` then starts it on the target after register (`startInstance` cause `post-move`); a Stopped instance stays Stopped (idea#474). `processInstance` alone would not start it, because `stopInstance` left the record Stopped and `shouldAutoStart` skips that status. A down failure is logged and does not fail the move or roll it back; a failed copy never takes the source project down, so rollback can still restart the source. Unused leftover networks labelled `com.docker.compose.project=<id>` on this Engine are then pruned; the shared `frontend`/`backend` networks are never removed, nor a network that still has containers attached.
- **Usage:** `moveApp <instanceId|instanceName> <sourceDiskId> <targetDiskId>`. The instance resolves id-first (see [Instance arguments](#instance-arguments)). Refused when the instance folder holds a symlink that resolves outside it (see [Instance data links](#instance-data-links)).
- **Failed same-Engine move:** the Operation is `Failed` and the command trace ends as `error`, with `errorCode` `COPY_FAILED` and `errorMessage` starting `MOVE FAILED: …; source kept` (idea#475; same leading-code style as a cross-Engine failure). A mid-move error is rethrown after cleanup and a source restart, so the trace cannot stay `ok`.
- **Across Engines** (capability `moveAppCrossEngine`, idea#79): when the target disk is docked to another Engine, the move keeps the same instance id (and its Backup Disk link) in one `moveApp` operation with steps `Copying`, `Checking`, `Removing the old copy` and an `Operation.move` record (shapes: `src/data/MoveAppShapes.ts`). 1) The existing cross-Engine copyApp path copies it into `instances/<same id>` (internal `dstId` only; not on the CLI) and keeps the name; a plain `copyApp` still gets a fresh id. `storedOn` stays on the source until after verify; no second instanceDB row is written. 2) The target Engine runs `verifyMoveTarget` (read-only; it runs outside that Engine's serial command queue so it does not wait behind `startInstance`): the folder on `operation.args.targetDiskId` (not `storedOn`), instance data size matches (within 1 MB or 1 %), and the port-ready registry is stable when the source was running; it writes the verdict into the operation. The source waits for that verdict on the Automerge document `change` event, with a 250 ms poll as fallback (idea#498). Ephemeral `idea/progress` `{ type, opId, step, bytesDone, bytesTotal }` is emitted at the start of the Copying step. 3) Only after a recorded good verify, `storedOn` flips to the target disk and only the source folder is quarantined (helper v4, never rm). `removeInstance` is not used, so the store row and Backup Disk link stay. Copy or verify failure deletes nothing: `MOVE FAILED: <reason>; source kept`. A failed removal after a good copy: `MOVED, source not removed: <reason>` (status Done, `SOURCE_NOT_REMOVED`). The source is kept stopped from the copy until removal (a failed move restarts it); if it was started (status or `lastStarted` changed) or written to (helper size changed) after the copy began, it is not removed: `MOVED, source not removed: the source was started/written to during the move …`, code `SOURCE_CHANGED`. Success: `MOVED to <Engine>`. Refused before anything happens (`MOVE FAILED: …; source kept`, codes `NOT_FOUND`, `AMBIGUOUS`, `SOURCE_REMOTE`, `TARGET_UNREACHABLE`, `PEER_ACCESS`, `TARGET_OUTDATED` (target lacks the capability), `HELPER_OUTDATED` (helper < v4), `BUSY`, `INVALID`, `TARGET_EXISTS` (the same id is already on the target disk or Engine)). An Engine restart never retries it and never removes the source (`INTERRUPTED` and only an unverified target folder is cleaned up, or `SOURCE_NOT_REMOVED` when verify was already recorded, with `storedOn` flipped if needed so a leftover source folder is not claimed). Every outcome carries a stable code (`MOVE_CODES` in `MoveAppShapes.ts`) in `Operation.move.code` and the trace `result.code`; refusals and failures also end the trace as `error` with `errorCode` = the code and `errorMessage` = the text. Verify failures are split: `VERIFY_NOT_FOUND`, `VERIFY_NOT_RUNNING`, `VERIFY_SIZE`, `VERIFY_TIMEOUT` (`VERIFY_FAILED` only as fallback). Any command error that carries an upper-case `code` writes it to the trace `errorCode`. The command trace result is the `MoveResult`.
- **Scope:** `engine`

### `verifyMoveTarget`
- **Description:** Internal, Engine → Engine (idea#79): the source Engine of a cross-Engine `moveApp` sends it to the target Engine, which checks the copy and writes `{ ok, code, bytes, detail, at }` into the move operation's `move.verify`. Not for the Console.
- **Usage:** `verifyMoveTarget <opId> <instanceId> <expectedBytes> <true|false>`
- **Scope:** `engine`

### `backupApp`
- **Description:** Refused with `NOT_DEMO` for a demo instance (engine#369; demo instances are excluded from backups, including `addBackupLink`).  Backs up an app instance to a Backup Disk. The default `x-app.backup.method` is `stop`: the Engine stops the instance briefly, runs a BorgBackup archive, then restarts it. **`method: hook` (idea#444):** while holding the instance lock, the Engine runs the App's `preHook` with `timeout … docker compose exec -T [--user] -- <service> <command…>` from the instance directory (no shell), then `borg-create` without stopping the compose project, then the optional `postHook`. `postHook` always runs, even after a failed or timed-out `preHook`. If `preHook` fails or times out, `fallback` (default `stop`) either takes the short-stop path and records `HOOK_FALLBACK` on the operation, or `fail` refuses with `HOOK_FAILED` without stopping. A `postHook` failure after a successful `borg create` leaves the backup `Done` and records `HOOK_POST_WARNING` on the operation (`args.warning` and `stepLabel`). `live` and `none` fail closed until an App needs them. Optional `hookExclude` (same path rules as `exclude`, including multi-segment directory paths such as `data/backup/daily`) is applied only when the preHook succeeded, so a live copy does not pack files the dump replaces (for example a SQLite db and its `-wal`/`-shm`). On `HOOK_FALLBACK` those paths are dropped and the now-stopped live files are packed; `exclude` is still applied in both cases (secrets such as keys and Tailscale state). Hooks do not bump the helper (v8). Restore does not apply the dump — the App entrypoint does that. If no Backup Disk name is given, the first docked Backup Disk linked to the instance is used. The backup holds the instance lock and the Backup Disk lock together (idea#126); if another operation holds either, the backup is not started and the command fails with the reason. A failure during the backup fails the command with its message. **`x-app.backup.exclude` (idea#443):** paths declared on the instance compose are passed through to `idea-app-data borg-create` (helper v8) and excluded from the archive (path-prefix, confined to the instance folder; a bare name other than `data` means `data/<name>`). A non-empty list on a helper older than v8 fails with `HELPER_OUTDATED` before any hook or stop and without writing `lastBackup`. **Cleanup (idea#401, helper v10 since idea#450):** after a successful backup, and before a backup if space looks tight, the Engine deletes oldest eligible archives (round-robin across instances, never the newest 3 or an instance's only backup) when free space is below 15 % until it is above 25 %, then `borg-compact`. An older helper (v9 included: its `borg-list` printed no archive list on real borg, idea#450) skips cleanup (`HELPER_OUTDATED` recorded) and the backup still runs. If the next backup's estimated size still does not fit after cleanup, the command fails with `BACKUP_DISK_FULL` ("Backup Disk full: add a bigger disk") before any hook or stop. The helper still refuses `system` as a Backup Disk *target* (source `system` stays allowed); `.env` and `operators.json` stay in the archive because a restore needs them.
- **Usage:** `backupApp <instanceId|instanceName> <backupDiskId>` (idea#168). The instance is an instance id or a unique instance name (see [Instance arguments](#instance-arguments)); the disk goes through the shared disk resolver (see [Disk arguments](#disk-arguments)). Every refusal ends the command trace as `error` with the reason. The trace arg keys stay `instanceName` and `backupDiskId`.
- **Result per attempt (idea#400):** each attempt writes `Instance.lastResult` (`{ time, method, result }`) and appends to `Instance.backupHistory` (the newest 7), manual or automatic. `result` is `OK`, `HOOK_POST_WARNING`, `HOOK_FALLBACK`, `HELPER_OUTDATED` (cleanup skipped, the backup is good; or the refusal of an exclude list on an old helper), `BACKUP_DISK_FULL`, `APP_DISK_NOT_DOCKED`, `SKIPPED_LOCKED`, `INTERRUPTED` (a stale lock found at dock, recorded once) or `FAILED`. `lastBackup` stays the last success. A backupApp never moves the schedule's `lastRun` in BACKUP.yaml.
- **Locked:** a direct `backupApp` with a waiting caller (Console, CLI, or a Console command forwarded by another Engine) while the instance or the Backup Disk is locked is refused with a leading `BUSY:` and records no result. Anything without a caller (an `immediate`-mode backup on dock, now cause `disk-docked`; an App Disk dock; crash recovery; the scheduler) records `SKIPPED_LOCKED`, and its trace starts with `SKIPPED_LOCKED:` (idea#400 Q4, Steve #347 call 4). While a scheduled run holds the lock, the `BUSY:` text ends with "a scheduled backup is running on this Backup Disk" (idea#400 PR C).
- **One code per attempt:** precedence `FAILED`, `SKIPPED_LOCKED`, `HOOK_FALLBACK`, `HOOK_POST_WARNING`, `HELPER_OUTDATED`, `OK` (Steve, #347 call 2). `BACKUP_DISK_FULL`, `APP_DISK_NOT_DOCKED` and `INTERRUPTED` are single-outcome failures.
- **Scheduled runs (idea#400 PR C, docs/BACKUP_SCHEDULE.md):** a `scheduled` Backup Disk docked to this Engine runs `backupInstance` for each link, one after another, from the Engine's 60 s tick (never host cron), with operation cause `scheduled-backup`. A held lock records `SKIPPED_LOCKED` and catches up once when the lock frees, inside the same window; a `FAILED` attempt is retried once after 60 s; an instance with a stale lock is not run (idea#446: `clearBackupLock`, then `backupApp`). Crash recovery never retries a `scheduled-backup` operation: it is marked `Failed` with `INTERRUPTED:`. While fullness cleanup deletes archives, `Disk.cleaning` is `true` and `Disk.cleaningStartedAt` is set (any backup, manual or scheduled).
- **Scope:** `engine`

### `restoreApp`
- **Description:** Restores the latest backup archive for an instance from any docked Backup Disk onto a target disk. Extracts the archive and calls processInstance to register and start the restored instance.
- **Usage:** `restoreApp <instanceId|instanceName> <targetDiskId>` (idea#168). The instance is an instance id or a unique instance name (see [Instance arguments](#instance-arguments)); the target disk goes through the shared disk resolver (see [Disk arguments](#disk-arguments)). Every refusal ends the command trace as `error` with the reason. The trace arg keys stay `instanceName` and `backupDiskId` (the latter holds the target disk).
- **Scope:** `engine`
- **Restore to another disk (#189):** before registering, the app master (`apps/<appId>`) and the instance's service tars (`services/<image>.tar`, named with `serviceImageTarName` so a pinned `repo:tag@sha256:…` finds the `repo:tag` file, idea#445) are copied onto the target when missing, from the previous `storedOn` disk first, then the other locally docked disks. Files already on the target are left alone; a piece found nowhere is logged and does not fail the restore. Code: `src/data/RestoreAppFiles.ts`.
- **Restore to another disk (#190):** when the instance was stored on another disk docked to this Engine and that disk still has `instances/<id>`, the old pre-restore folder is quarantined after the instance is registered on the target, with the helper v4 op `idea-app-data quarantine` (to `<old disk>/.idea-quarantine/<id>-<UTC stamp>`; never deleted, it may be newer than the backup). The quarantine path is logged in the command trace. A helper older than v4 refuses the restore up front with `HELPER_OUTDATED`; a failed quarantine is logged and leaves the folder in place. Code: `src/data/RestorePreQuarantine.ts`.

### `listBackup`
- **Description:** Lists Borg archives for an instance on a docked Backup Disk (helper v10 `borg-list`, idea#450). With an optional archive name, also lists member paths (capped; `partial: true` when truncated). Does not stop the instance, does not take the instance lock, and may run while the App is Running. The result (archives, optional members, whether a `.backup-in-progress` lock is present) is attached to the command trace. Refuses when the disk is not a Backup Disk, is this Pi's system disk, is undocked, has no repository for the instance, the helper is older than v10 (`HELPER_OUTDATED`; v9's `borg-list` printed no archive list on real borg, idea#450), or `skipBorg` is set. Capability `backupVerify` (idea#446; helper v10).
- **Usage:** `listBackup <instanceId|instanceName> <backupDiskId> [archive]`. The instance is an instance id or a unique instance name (see [Instance arguments](#instance-arguments)); the disk goes through the shared disk resolver (see [Disk arguments](#disk-arguments)). At most one archive name. Every refusal ends the command trace as `error` with the reason.
- **Scope:** `engine`

### `verifyBackup`
- **Description:** Restores a backup archive into a scratch folder on the Backup Disk itself, `<backup disk>/.idea-verify/<instanceId>-<stamp>/` (root-owned 0700 via helper v9 `borg-extract-verify`), and checks it without disturbing the live instance: no stop/start, no instance lock, no write under `instances/<id>`, no containers, no `processInstance`. The scratch folder is never auto-deleted. Path checks always include `x-app.backup.exclude` (must be absent in the archive) plus optional `x-app.backup.verify.present` / `verify.absent` on the *live instance compose* (same path rules as `exclude`: a bare name other than `data` or a leading-dot file such as `.env` is `data/<name>`; no hook/stop guessing). The result on the command trace includes `archive`, `scratchPath`, `members` (or a cap + `partial: true`), per-path pass/fail, `ok`, and sizes (`archiveOriginalBytes`, `archiveCompressedBytes`, `neededBytes`, `freeBytes`, `scratchBytes`). `scratchBytes` is the helper v12 (idea#460) count: `borg-extract-verify` runs `du -sb -x` on the root-owned 0700 extract and prints `scratchBytes=<n>`; the Engine uses that value. The Engine runs as `pi` and cannot size that tree itself (a local walk reports 0). An older helper that does not print the count still verifies (`BACKUP_VERIFY_HELPER_MIN` stays v10); `scratchBytes` is then `null`. There is no store field for verify space: space is checked up front (`original_size * 1.1`, or `compressed_size * 2` when original is missing) against the disk's free bytes and reported in the result; too little space is `NO_SPACE`. Takes only the Backup Disk lock. Refuses if `backupApp` is Pending/Running on that disk, the disk is locked, the archive is missing, the helper is older than v10, or `skipBorg` is set. The system disk is never a Backup target. Capability `backupVerify` (idea#446).
- **Usage:** `verifyBackup <instanceId|instanceName> <backupDiskId> [archive]`. Without an archive name, the newest archive is used. At most one archive name. Every refusal ends the command trace as `error` with the reason.
- **Scope:** `engine`

### `clearBackupLock`
- **Description:** Removes only the `.backup-in-progress` lock file for an instance on a docked Backup Disk, and drops the matching `Disk.backupStaleLocks` entry. Never starts a backup (idea#446: boot no longer auto-retries a leftover lock). When the lock file is already gone but `Disk.backupStaleLocks` still lists the instance, it drops only the store entry (result `lockFileRemoved: false`, idea#454). Refuses if a `backupApp` of that instance to this disk is Pending/Running, the in-memory backup mutex is held, or the disk is locked (those still end the trace as `error`). When there is neither a lock file nor a stale-lock entry, nothing is cleared (`cleared: false`); the command returns the plain message `no backup lock to clear for <instance>`, writes it as an info log line, and ends the trace as `ok` with that result, so the Console does not show an error (idea#454). Capability `backupVerify`.
- **Usage:** `clearBackupLock <instanceId|instanceName> <backupDiskId>`. Refusals other than "nothing to clear" end the command trace as `error` with the reason.
- **Scope:** `engine`

### `removeBackupRole`
- **Description:** Drops the Backup role from a docked disk without touching App or Files roles. Quarantines `backups/` to `.idea-quarantine/backups-<stamp>/` (helper v9 `quarantine-backups`; never deletes), unlinks `BACKUP.yaml`, and runs `processDisk`. Refuses if a stale `.backup-in-progress` lock is still present or `Disk.backupStaleLocks` is non-empty (clear it first), if `backupApp` is running to the disk, or if the disk is locked. If `backups/` is already absent, only `BACKUP.yaml` is removed. Capability `backupVerify` (idea#446).
- **Usage:** `removeBackupRole <diskId>`. The disk goes through the shared disk resolver (see [Disk arguments](#disk-arguments)). Every refusal ends the command trace as `error` with the reason.
- **Scope:** `engine`

### `addBackupLink`
- **Description:** Links one more instance to a docked Backup Disk without rewriting the other links (idea#451). Reads `BACKUP.yaml` as a YAML document and appends `{instanceId, lastBackup: 0}` to `links`; `mode`, every other link with its own `lastBackup`, their order, comments and any other keys (for example a future `schedule`) are left as they are. The file is written atomically (temp file in the same folder, fsync, rename), so a failure leaves the old file. `Disk.backupConfig.links` gets the id in the store. No `processDisk` and no backup, even in `immediate` mode: the next backup comes on the next dock or `backupApp`. Takes the Backup Disk lock while it edits. A stale lock recorded for the instance does not block an add. Capability `backupLinks`.
- **Usage:** `addBackupLink <instanceId|instanceName> <backupDiskId>`. Local-only: the instance resolves like in `createBackupDisk` (an id, or a name unique on this Engine, stored on a disk docked here). The disk goes through the shared disk resolver rules (see [Disk arguments](#disk-arguments)).
- **Result** (`CommandTrace.result`): `{ backupDiskId, instanceId, links, added: true, note: "next backup on the next dock / backupApp" }`; `links` is the full list after the edit.
- **Scope:** `engine`

### `removeBackupLink`
- **Description:** Removes one link from a docked Backup Disk's `BACKUP.yaml` without touching the others (idea#451). Same document edit, atomic write, store update (`Disk.backupConfig.links` loses the id) and disk lock as `addBackupLink`; no `processDisk`. Never touches `backups/<id>/`: the repository stays (its removal is a separate, deliberate step). Capability `backupLinks`.
- **Usage:** `removeBackupLink <instanceId|instanceName|rawId> <backupDiskId>`. A raw id that is in `links` works even when the instance is no longer in `instanceDB` (removed or quarantined); a name must resolve to a linked instance.
- **Result** (`CommandTrace.result`): `{ backupDiskId, instanceId, links, removed: true, repoLeft }`; `repoLeft` is the path of `backups/<id>/` when it still exists, else `null`.
- **Scope:** `engine`

**Refusal codes for `addBackupLink` / `removeBackupLink`** (start of the error text; the trace ends as `error` and nothing is written): `NOT_DOCKED` (unknown disk, not docked, or docked to another Engine), `AMBIGUOUS` (a disk or instance name that matches more than one; use the id), `SYSTEM_DISK`, `NOT_A_BACKUP_DISK` (no Backup role), `BAD_BACKUP_YAML` (missing, unparsable, or not `{mode, links[]}` with an `instanceId` on every link), `INSTANCE_NOT_FOUND` (add only: unknown, or not on this Engine), `ALREADY_LINKED` (add), `NOT_LINKED` (remove), `BUSY` (the Backup Disk lock is held, or a `backupApp` to the disk is Pending/Running), `BACKUP_IN_PROGRESS` (remove only: `backups/<id>/.backup-in-progress` exists or the id is in `Disk.backupStaleLocks`; run `clearBackupLock` first). The older backup commands (`listBackup`, `verifyBackup`, `clearBackupLock`, `removeBackupRole`) keep their uncoded messages for now.

### `setBackupMode`
- **Description:** Switches a docked Backup Disk between `immediate`, `on-demand` and `scheduled`, and sets the daily time of a scheduled disk (idea#400 PR D, docs/BACKUP_SCHEDULE.md). Runs on the Engine the disk is docked to. `BACKUP.yaml` is edited as a document with the atomic writer, and only `mode` and `schedule` change: links and their `lastBackup`, `lastRun`, the uptime counter, comments and unknown keys stay. The store `Disk.backupConfig` (`mode`, `schedule`, `scheduleError`) is updated in place, under the Backup Disk lock; there is no `processDisk` and no backup is started. Capability `scheduledBackups`.
- **Usage:** `setBackupMode <backupDiskId> <immediate|on-demand|scheduled> [HH:MM]`. The disk goes through the shared disk resolver rules (see [Disk arguments](#disk-arguments)). The time is 24 h Pi-local (`H:MM` is accepted and stored as `HH:MM`) and is valid only with `scheduled`.
- **Schedule rules:** `scheduled HH:MM` sets `schedule: { daily: HH:MM }`. `scheduled` with no time keeps a valid schedule, or writes 02:30 when there is none or it is invalid (the same rule as `createBackupDisk`). `immediate` / `on-demand` leave `schedule` in the file, so switching back to `scheduled` keeps the time. A scheduled disk that never ran, or whose most recent slot comes after its `lastRun`, runs at the next tick (within a minute).
- **Result (trace):** `{ backupDiskId, previousMode, mode, schedule: {daily}|null, scheduleError: string|null, changed: boolean, note }`. `changed: false` means the file already had that mode and schedule, so nothing was written.
- **Refusal codes** (start of the error text; the trace ends as `error` and nothing is written): `NOT_DOCKED`, `AMBIGUOUS`, `SYSTEM_DISK`, `NOT_A_BACKUP_DISK`, `BAD_BACKUP_YAML` (the same meanings as for `addBackupLink`), `BAD_MODE` (not one of the three modes), `BAD_TIME` (not `HH:MM` 00:00–23:59, a time with a mode other than `scheduled`, or more than one time), and `BUSY` (the Backup Disk lock is held, or a `backupApp` to the disk is Pending/Running, which includes a scheduled run).

### `removeInstance`
`removeInstance <instanceId>` (capability `removeInstance`, idea#347). Removes a stopped instance on a disk docked to this Engine without deleting any data. Under the instance lock it runs `docker compose -p <id> down` (never `-v`, so named volumes are kept), then the root helper `idea-app-data quarantine <root> <id>` (helper v4) renames `instances/<id>` to `<disk>/.idea-quarantine/<id>-<UTC stamp>` (root-owned, 0700). Only then is the instance record dropped from the store. Unused networks labelled `com.docker.compose.project=<id>` on this Engine are then pruned (idea#468); the shared `frontend`/`backend` networks are never removed, nor a network that any container still references, running or stopped (`docker ps -a --filter network=<id>`). A prune failure is logged and does not fail the command. The `removeInstance` log entry and History name the quarantine path and the kept volumes. For a strict instance id and helper v14+, `removeInstance` first calls `quarantine-snapshot` so `.pre-update/<id>` is moved to `.idea-quarantine` (idea#396; a failure is logged and removal continues). After a successful remove, `Disk.preUpdateSnapshots`, `Disk.preUpdateBytes` and `Disk.quarantineBytes` are refreshed from the helper (idea#428), the same way `updateApp` refreshes them after a snapshot. The removed instance's own snapshot entry is then dropped from the disk row (and subtracted from `preUpdateBytes`) even if `.pre-update/<id>` is still on disk. `quarantineBytes` comes from the helper, so it includes the new `.idea-quarantine/<id>-<stamp>`. Nothing is ever purged automatically; clearing `.idea-quarantine` needs Koen's OK. Disk scans, listing, backups and space accounting ignore `.idea-quarantine`.

**Instance ids (idea#479).** The id is checked before any compose or Docker action. `removeInstance` is the only command that accepts a legacy dotted id written by an older Engine (e.g. `nextcloud-yj8ral61js46bphogbi.backup-20261027-181633`: dot-separated `[a-z0-9-]` segments, each starting with `[a-z0-9]`, at most 128 characters); it needs helper v13 for that, whose `quarantine` accepts the same form (every other helper subcommand stays strict). Compose drops the dot, so `-p`, the leftover-container fallback, the kept-volume list and the network prune all use the compose project name, derived as compose-go `NormalizeProjectName` does (lowercase, keep only `[a-z0-9_-]`, trim leading `_`/`-`), and match containers on the exact `com.docker.compose.project` label. A dotted id whose project name equals another instance's is refused (`PROJECT_CLASH`). `updateApp`, `moveApp` and `eraseDisk` refuse a dotted or otherwise invalid id with `INVALID_INSTANCE_ID` before any Docker action (`eraseDisk` checks every instance on the disk: remove such an instance first); `forgetDisk --with-instances` skips the network prune for such an id (logged).

Refusals (code at the start of the error text; the store is untouched): `NOT_FOUND`, `NOT_LOCAL`, `AMBIGUOUS`, `INVALID_INSTANCE_ID` (neither a strict id nor a legacy dotted id), `PROJECT_CLASH`, `RUNNING` (Running/Starting), `BUSY_BACKUP` (backup/restore holds the lock), `BUSY_MOVE` (move/copy holds it), `BUSY` (other holder), `COMPOSE_DOWN_FAILED`, `QUARANTINE_FAILED`, `HELPER_OUTDATED` (root helper older than v4, or older than v13 for a dotted id).

**Helper version:** the Engine always starts, whatever `idea-app-data` version is installed; a missing or different helper is only logged as a warning at startup. Commands that need a newer helper refuse with `HELPER_OUTDATED`: `removeInstance` and a cross-Engine `moveApp` need v4 (`removeInstance` needs v13 for a legacy dotted id, idea#479), `updateApp` v5, `backupApp` with a non-empty `x-app.backup.exclude` needs v8 (idea#443), and `listBackup` / `verifyBackup` / `clearBackupLock` / `removeBackupRole` (and backup cleanup, idea#401) need v10 (idea#446; idea#450 fixed v9's `borg-list` inventory). A backup with no excludes still runs on v7. This Engine speaks helper v13 (`APP_DATA_HELPER_VERSION`; idea#479: `quarantine` accepts a legacy dotted id; v12, idea#460: `borg-extract-verify` prints `scratchBytes=<n>`). `verifyBackup` still runs on v10, with `scratchBytes` null. No new sudoers line.

### `updateApp`
`updateApp <instanceId|name> <newAppId> [--allow-major] [--source <diskId>]` (capability `updateApp`, #230, proposal idea#351). Updates an instance to a newer bundle `apps/<newAppId>/` on a disk docked to this Engine, or — with `--source <diskId>` naming a disk docked to another Engine — fetched first (cross-Engine Fetch, capability `updateAppFetch`, #263; see below). Needs root helper `idea-app-data` v14 (idea#396: snapshot/estimate excludes under `data/`, `quarantine-snapshot`, and the 24 h pre-update cleanup). For a demo instance, Swap restamps `x-app.demo` from the old compose (it is not dropped) and sets `Instance.demoPackWarning` when the on-disk pack is below the new bundle's `minVersion` (engine#369; a missing pack does not set a warning).

Steps (progress: ephemeral message `idea/updateProgress` with `{engineId, instanceId, step, bytesDone, bytesTotal}`; also the `updateApp` operation's step): Fetch, Check, Snapshot, Swap, Start, Health.

**Cross-Engine Fetch (#263, capability `updateAppFetch`).** Push model: under the instance lock, before anything is stopped, the target Engine writes `apps/<newAppId>/.idea-fetching` (request id) on the instance's disk and sends `pushAppBundle <sourceDiskId> <appId> <targetEngineId> <targetRoot> <requestId> <instanceId>` to the source Engine. The source refuses bundles carrying bundle-root `.idea-*` files or no `SHA256SUMS`, and pushes with `rsyncToPeer` through the existing `receive-app` path with `--partial`, 3 retries with backoff (5 s, 20 s, 60 s). It answers `appFetchResult <requestId> ok|TRANSFER_FAILED <why>`. The target refuses pushed bundle-root `.idea-*` files, re-checks `SHA256SUMS`, then renames `.idea-fetching` to `.idea-fetched`. Dock and the app listing ignore a folder until `.idea-fetched` exists; a partial or refused folder is moved aside to `apps/.idea-aborted-<appId>-<stamp>/` (never removed). Any failure refuses `TRANSFER_FAILED` with nothing stopped. Thermal pause: at ≥75 °C the source pauses (stopping a running rsync; not counted as a retry) until ≤65 °C, broadcasting `idea/updateProgress` with `fetchPaused: {reason: 'thermal', bytesDone, bytesTotal, since}`. No helper or gate change.
- **Identity (idea#448, idea#396).** The snapshot and the read-only `estimate` leave out the union of the live and the new compose's `x-app.backup.exclude` and the live compose's top-level `x-app.snapshotExclude` (for usage-dashboard `data/keys`, `data/tailscale`, `data/tailscale-run`). A rollback's `restore-snapshot` gets only `live.backup.exclude ∪ current.backup.exclude` (the helper also applies the snapshot's recorded `EXCLUDE`); it never writes, deletes or moves those paths, so the Tailscale state file keeps its inode and the node keeps its identity. Tokens must be `data` or `data/<rel>` after v8 normalisation (a bare name becomes `data/<name>`), at most 256 characters after trimming and 32 unique entries. A refused list (`volumes/…`, a symlink leaving `data/`, a too-long or too-large list, or a helper `refused:`) refuses `INVALID_EXCLUDE` before anything is stopped, estimated or written. A new bundle that itself contains one of those paths (or a non-directory where a parent of one should be) refuses `BUNDLE_CONTAINS_EXCLUDED`, naming the paths and which list they hit (`x-app.backup.exclude` or `x-app.snapshotExclude`), before the Snapshot: nothing is stopped, backed up or written.
- **Pre-update backup (idea#448).** A major update (an unversioned SHA to a tag stays major, idea#76; `--allow-major` is still required) with no backup in the last hour no longer needs a separate `backupApp`: when a Backup Disk linked to the instance is docked to this Engine, `updateApp` takes the backup itself. It is a backup of the CURRENT instance, so it uses the current (live) compose's `x-app.backup` (`instances/<id>/compose.yaml`), never the new bundle's (idea#458: a hook that only the new version ships ran inside the old containers and exited 127). With `method: hook` in the current compose and the instance running, the current compose's preHook runs (`docker compose -p <id> --project-directory instances/<id> -f instances/<id>/compose.yaml exec`, against the live containers and data) and Borg runs before anything is stopped; a failed preHook refuses `HOOK_FAILED` ("… (the current version's backup hook); nothing was stopped or changed, and the update does not fall back to a stop-mode backup") whatever its `fallback` says. With `method: stop` or no `x-app.backup` in the current compose (an update that introduces a hook backs up the old version in stop mode), or when the instance is not running, Borg runs inside the one Snapshot stop (no second stop). The new bundle's `x-app.backup` only adds its `exclude` list to the snapshot excludes. The backup honours `exclude` (and `hookExclude` after a good preHook), sets `lastBackup` and shows as a `backupApp` operation with `reason: pre-update`. Any other backup failure refuses `BACKUP_FAILED`, including a `.backup-in-progress` left by an earlier backup (`BACKUP_STALE_LOCK`, not retried, idea#446); if the instance was stopped for it, the old version is started again. Without a linked docked Backup Disk the refusal is still `NEEDS_BACKUP`.
- **Check** refuses before anything changes. Its space check uses the helper's read-only `estimate` (instance folder + named volumes, net of the snapshot exclude list, and the App Disk's free space), so `NO_SPACE` refuses before the instance is stopped; the snapshot's own check stays as a backstop.
- **Snapshot** stops the instance and waits until its containers are gone. Then `idea-app-data snapshot` copies `instances/<id>` (bundle files, `.env`, data) to `<disk>/.pre-update/<id>/` (root, 0700). Each named Docker volume of the instance (compose project `<id>`) is exported too, to `.pre-update/<id>/volumes/<volume>.tar`: offline, with the host's GNU tar from the local volume folder (no image is run or pulled), keeping owners, modes, ACLs and xattrs; each archive is listed (`tar -t`) and checksummed (`volumes/SHA256SUMS`, re-checked) before `COMPLETE`. The export time per volume is in the op log and the result. A `COMPLETE` marker is written last; a snapshot without it is never restored. A previous snapshot of the same instance (complete or not) does not block a second update: it is renamed (same disk, never copied or removed) into `.idea-quarantine/pre-update-<id>-<stamp>` first, and that path is reported.
- **Swap** copies the new bundle files over the instance folder (`.env` kept) and sets `x-app.instanceName` again.
- **Health** waits for healthy within `x-app.healthTimeout` (defaults: Kolibri 900 s, Nextcloud 300 s, others 600 s; the same table, `src/data/AppHealthTimeout.ts`, gives the start-time port-ready budget of `startInstance`). `starting`/`unhealthy` mean "wait"; an exited container, a crash loop (3 restarts) or the timeout fail. On a pass, the Engine writes `Instance.preUpdateGate` `{ at, bootId, uptimeS }` (`at` is wall-clock ms if the clock is trusted per idea#400 / `evaluateClockTrust`, else null). A scanner at start, on dock and hourly then calls `quarantine-snapshot` once 24 h have passed (trusted `at + 24 h`, or the same boot's uptime since the gate), without blocking updateApp or startup; `settings.quarantineAfterMs` may shorten that window only in isDev or test mode. The field is cleared after a successful or no-op quarantine, a new snapshot of that id, a rollback, or `removeInstance`. Capability `preUpdateQuarantine` is advertised when the startup helper check sees v14+.
- A failure from Snapshot on rolls back: compose down (no `-v`), `restore-snapshot` in place with the same excludes (`instances/<id>` is never moved; every live file it replaces or deletes goes to `.idea-quarantine/<id>-before-restore-<stamp>/` first; each volume's current contents are renamed to `_data.idea-quarantine-<stamp>` beside it before the archive is extracted), old version started. The error starts `ROLLED BACK: <why>`. If the rollback fails, the instance is left Stopped with a status starting `ROLLBACK FAILED:`.
- The result and History carry `snapshotPath`, `snapshotBytes`, `previousSnapshotQuarantinedAt` (or null), `volumes` (`{name, bytes, exportMs}`), `snapshotExcludes` and `preUpdateBackup` (`{backupDiskId, method, duringStop}` or null, idea#448). Snapshots are kept; `Disk.preUpdateSnapshots` lists `{instanceId, sizeBytes, complete}` per disk, and `Disk.preUpdateBytes` / `Disk.quarantineBytes` give the totals of `.pre-update` and `.idea-quarantine`. Nothing is purged automatically.
- An Engine restart during an update rolls back at startup when the snapshot is complete and the swap had started (in place, with the snapshot's `EXCLUDE` plus the excludes of the compose now in the folder); the operation ends Failed with `INTERRUPTED: ...`.

Refusal codes (start of the error text): `NOT_FOUND`, `AMBIGUOUS`, `NOT_DOCKED`, `INVALID_INSTANCE_ID` (idea#479: a legacy dotted or otherwise invalid id, checked before anything is stopped), `HELPER_OUTDATED` (helper older than v14), `BUSY`, `SOURCE_MISSING`, `NO_SUMS` (the bundle has no valid `SHA256SUMS`, root-relative, checked with `sha256sum --check --strict`; such an App is never offered an update), `DIFFERENT_APP` (names the missing or mismatched `x-app.name` and/or `x-app.version`, with actual and expected values), `NOT_NEWER`, `MAJOR_NOT_ALLOWED`, `NEEDS_BACKUP` (major update without a backup in the last hour and no linked Backup Disk docked here), `BAD_BACKUP_SPEC`, `HOOK_FAILED`, `BACKUP_FAILED` (idea#448, the pre-update backup), `INVALID_EXCLUDE` (idea#396, a snapshot/estimate exclude is refused), `BUNDLE_CONTAINS_EXCLUDED` (idea#448 / idea#396, the bundle ships an excluded path; the text names the list), `NO_SPACE` (`NO_SPACE: ... snapshot needs X, free Y`; the snapshot needs the instance folder plus its named volumes, which may live on the system SSD, plus 10 %, at least 1 GiB, all against the free space of the instance's App Disk). Reserved: `TRANSFER_FAILED` (#263 only), `SOURCE_UNSUPPORTED` (not emitted in v1).

`Instance.updateAvailable`: `{appId, sourceDiskId?, sourceEngineId?, fromVersion?, toVersion?, major?, estimatedMinutes?, sizeBytes?, migrationNote?}` or null. Filled at dock time, cheaply: a newer `apps/<name>-<version>/` of the same App on a disk docked to this Engine whose `SHA256SUMS` exists and lists `compose.yaml` (the file is read, not verified; the highest version wins). The full `SHA256SUMS` check runs at update start (`NO_SUMS`). Once an `updateApp` has started its operation it recomputes the field when it ends, whatever the outcome, from the instance's version at that moment (idea#459): after a successful update an offer of the version the instance now runs (or an older one) is cleared and only a genuinely newer bundle is still offered, with `fromVersion` the new version; after a rollback or a failure before the swap the old version runs and the offer stays. A refusal before the operation leaves the field untouched. A startup recovery of an interrupted update recomputes it too.

`Disk.appBundles` (idea#76 gap 1): `[{appId, version, sumsListed, sizeBytes, updatesFrom?, healthTimeout?, migrationNote?}]`, or null/missing when unknown (readers then fall back to the `--source` disk). Written only by the Engine the disk is docked to, on dock and only when the list changes; cleared on undock. Other Engines use it for the hint: a bundle with `sumsListed` true on a disk docked to an Engine that advertises `updateAppFetch` is offered with that Engine as `sourceEngineId`, and `sizeBytes` plus transfer time is added to the estimate. Hints are refreshed on any change to a disk's `dockedTo` or `appBundles`; a hint on an instance whose disk is docked nowhere is cleared.

### `setupDemo`
- **Description:** Installs this Engine's demo set (Kolibri and/or Nextcloud) on one App Disk (engine#369). Operators only is enforced in the Console; the Engine has no sender identity and does not check a role. One demo set per Engine: if a demo already lives on this target disk, the same command resumes; a demo on another docked disk is `DEMO_EXISTS`; demos on two or more docked disks are `DEMO_AMBIGUOUS`. App Disks only (`SYSTEM_DISK`, `NOT_APP_DISK`). Source order is a local `IDEA-DEMO` pack on a docked disk or USB stick, then the sha256-pinned GitHub release asset from the app bundle's `app.yaml`, else `NO_SOURCE` (offline downloads fail cleanly with `NO_SOURCE` or `PACK_OUTDATED` when the only local pack is older than `minVersion`). Without `--apps`, every app that has a usable source is set up; an app whose pre-check is `NO_SOURCE` is skipped (it is not in `Operation.demo.apps`). `NO_SOURCE` refuses the whole command only when no app has a source, or when an app named explicitly in `--apps` has none. Other pre-check codes still refuse the whole operation. The pack is extracted under `<instance>/demo-pack/x/`. Hooks are declared in `app.yaml` (`demo.steps`); only the app bundle's `demo/hook.sh` runs, never a script from the pack. `CREDITS.txt` is required; undeclared pack files are ignored and logged. The target disk is marked in use (`trackInFlight`) for the duration. Recovery is `fail` (`INTERRUPTED`); pressing the button again resumes. `minEngine` stays `'1.0'`; the Console gates on the `demoApps` capability (python3 on PATH, advertised at boot). If that check has not run yet, `setupDemo` runs it on demand and then refuses with `HELPER_OUTDATED` when python3 is missing; it never proceeds blind. `INVALID_PACK` is a bad or invalid `pack.json`, a missing or empty credits file, or an unsafe tar member; `CHECKSUM_MISMATCH` is only a sha256 mismatch.
- **Usage:** `setupDemo <targetDiskId> [--apps kolibri,nextcloud]`
- **Trace args:** `{ targetDiskId, apps }` with `apps` a comma-separated string (always present).
- **Operation:** `kind: 'setupDemo'`. `Operation.demo` is `{ targetDiskId, apps: [{ app, instanceId, steps: [{ id, status, bytesTotal? }], source, packVersion, code, detail }], skipped: [{ app, code: 'NO_SOURCE', detail }], code, resultText }`. `skipped` is always present (`[]` when nothing was skipped). Skipped apps are not in `demo.apps`. `resultText` names the skipped apps; the Operation ends `Done` when the attempted apps succeed. Stable step ids: `install`, `download`, `verify`, then hook ids from `app.yaml` with `start` and `ready` inserted before the first `needs: running` hook (Kolibri: `seed`, `start`, `ready`, `classwork`; Nextcloud: `start`, `ready`, `seed`). Errors are `CODE: text`. Ephemeral progress is `idea/progress` `{ type, opId, step, bytesDone, bytesTotal }` (bytesDone is not stored; bytesTotal is stored once on the download step).
- **Result:** `{ code: 'DEMO_READY', apps: [{ app, instanceId, name, port, source, packVersion }], skipped }`. `skipped` is a comma-separated `app:CODE` string on the command trace (empty when nothing was skipped).
- **Scope:** `engine`
- **Capability:** `demoApps` (not in the always-on list; see ARCHITECTURE.md)

### `removeDemo`
- **Description:** Stops and removes demo instances (engine#369). With no instance ids, every demo instance docked to this Engine is removed. Any id that is not a demo instance refuses the whole command (`NOT_DEMO`) before an Operation is created. Demo instances cannot be backed up, copied, or moved (`NOT_DEMO` on `backupApp` / `addBackupLink` / `copyApp` / `moveApp`).
- **Usage:** `removeDemo [<instanceId>...]`
- **Trace args:** `{ instanceIds }` as a comma-separated string (empty when removing every docked demo).
- **Operation:** `kind: 'removeDemo'` with `Operation.demo` as for `setupDemo` (steps `stop`, `remove`). Recovery is `fail` (`INTERRUPTED`); press again to retry. Errors are `CODE: text`.
- **Result:** `{ code: 'DEMO_REMOVED', removed: [{ instanceId, quarantinePath, keptVolumes }] }`.
- **Scope:** `engine`
- **Capability:** `demoApps`

### `createBackupDisk`
- **Description:** Writes a BACKUP.yaml configuration onto a docked disk, turning it into a Backup Disk. Specify the mode (`immediate`, `on-demand`, or `scheduled`) and one or more instance names to link. An existing BACKUP.yaml is edited as a document (idea#400): `mode` and `links` are replaced (kept links keep their `lastBackup`), and `schedule`, `lastRun`, the uptime counter and unknown keys stay. `scheduled` adds `schedule: { daily: "02:30" }` when the disk has no valid schedule, and the Engine's tick runs it (idea#400 PR C, see `backupApp` and docs/BACKUP_SCHEDULE.md). An invalid `schedule` in BACKUP.yaml is shown as `Disk.backupConfig.scheduleError` (the BAD_TIME / BAD_SCHEDULE text) and the disk still runs, at the 02:30 default, until it is fixed (Steve, #351 call 1). The whole file is rewritten and `processDisk` runs again; a link that was already in the file keeps its `lastBackup`, new links start at 0 (idea#451). To add or remove a single link, use `addBackupLink` / `removeBackupLink`.
- **Usage:** `createBackupDisk <diskId> <mode> <instanceName...>` (idea#128; the argument was `diskName`). The disk is resolved by the shared disk resolver (see [Disk arguments](#disk-arguments)). An unknown, undocked, remote or ambiguous disk, a bad mode or a missing store ends the command trace as `error` with the reason.
- **Scope:** `engine`


### `summariseDisk`
- **Description:** Content summary for erase confirmation (idea#134). Walks a mounted IDEA disk (or reports `readable: false` for an unformatted candidate) and stores the JSON `contentSummary` on `CommandTrace.result`. Caps: 100 000 entries or 10 s → `partial: true`. Backups from `BACKUP.yaml` + store (no `borg list`).
- **Usage:** `summariseDisk <diskId|candidateId>`
- **Capability:** `eraseDisk`

### `eraseDisk`
- **Description:** Erase any non-system disk to an empty IDEA disk (idea#134): GPT + one ext4 partition, label "IDEA Disk", only `META.yaml`, `diskTypes` `['empty']`. Requires a fresh `summariseDisk` trace (same target, &lt;10 min) and the exact label as confirmation. Eject path first; blockers for backup / instance lock / Nextcloud first-start|upgrade; `docker compose down -v` per instance; then unused networks labelled `com.docker.compose.project=<instanceId>` on this Engine are pruned (idea#468; never the shared `frontend`/`backend` networks, never a network that still has containers attached); instances and app entries removed (E9); backup links to an erased Backup Disk cleared. Script: `/usr/local/sbin/idea-erase-disk` (11-engine-files, no argument list).
- **Usage:** `eraseDisk <targetId> <summaryTraceId> <confirmName…>`
- **Capability:** `capabilities.includes('eraseDisk') && capabilitiesBootedAt === lastBooted`

### `createFilesDisk`
- **Description:** Adds the Files role to a docked disk (idea#131, Files Disk step 1): writes `FILES.yaml` and an empty `files/` folder in the disk root, plus `META.yaml` if it is missing (the disk ID is always kept), then processes the disk again so `diskTypes` gains `'files'` next to its other roles (for example `['app', 'files']` or `['app', 'backup', 'files']`). Works on an empty ext4 disk (`['empty']`) and on an App and/or Backup Disk. Nothing else on the disk changes: `apps/`, `services/`, `instances/`, `BACKUP.yaml` and `backups/` are untouched, existing instances keep running, and the filesystem label is never changed. Mounting `files/` into opted-in Apps is idea#133 (step 2): `createFilesDisk` ends with `processDisk`, which schedules a remount of other-disk opted-in instances (same-disk instances start with the override via `processAppDisk`).
- **Usage:** `createFilesDisk <diskId> [<shareName…>]`. The disk **ID** only (the command has no name form, so there is no name fallback). The share name is optional, takes the rest of the line and defaults to `School Files`: 1 to 16 characters from `A–Z a–z 0–9`, space, hyphen, underscore and parentheses, with no leading or trailing space (tokens are joined with one space). The trace records `args.diskId` and `args.shareName` (the tokens, `[]` for the default).
- **Refused** (the trace ends as `error`; nothing is written to the disk), checked in this order:
  1. a bad share name, or `Engine.eraseInProgress` is set for this disk;
  2. the ID is unknown, the disk isn't docked, or it is docked to another engine;
  3. the system disk;
  4. the disk is already a Files Disk (`'files'` in `diskTypes` or `FILES.yaml` present), an Upgrade Disk, or not processed yet (`diskTypes` empty);
  5. the root holds anything besides `META.yaml`, `lost+found` and its roles' IDEA entries (`apps/`, `services/`, `instances/` for an App Disk; `BACKUP.yaml`, `backups/` for a Backup Disk), including a stray `files/`: "<name> has other files on it (…). Use Make this a Files Disk to erase it, or empty it on another computer.";
  6. not ext4 (`findmnt -no FSTYPE /disks/<device>`);
  7. the disk is locked by another operation, or a backup to it is pending or running. This is checked before anything changes, and the disk lock is held until the files are written;
  8. the root isn't writable by `pi` and the owner change fails ("this Engine is missing a permission update; ask Ops to install the new 11-engine-files sudoers file"), or the root is still not writable afterwards.
- **Owner change:** only when `pi` can't write the disk root (a root-owned mount root). The trace first records the root folder's previous `uid:gid` and mode (so it can be undone by hand), then the Engine runs exactly `sudo /usr/bin/chown -h pi:pi /disks/<device>` (entry in `/etc/sudoers.d/11-engine-files`): the root folder only, not recursive, `-h` never follows a symlink. `createFilesDisk` is the only command that changes a disk root's owner.
- **Scope:** `engine`
- **Examples:**
  - `createFilesDisk f3a9c2d1` — share name "School Files"
  - `createFilesDisk f3a9c2d1 My Share (2)` — share name "My Share (2)"

### `ejectDisk`
- **Description:** Safely ejects a docked disk from this engine. Updates the shared store to reflect the undocked state, stops all running instances on the disk, then unmounts it: `umount` is repeated (at most 5 times, 1 s apart after a failure) until the mount point is no longer a mount point, and the empty mount point is removed with `rmdir`, never `rm -fr` (idea#126). If it stays busy, nothing is removed, a failed `diskDetection` trace is written and the disk gets `unmountError` (restart the Pi to release it). Refused for this Pi's system disk (the record marked `diskTypes: ['system']`, or any record on the drive holding `/` and `/boot/firmware`), whether it is named by id or by name (idea#152). Refused while the disk is locked by an operation or while a `backupApp` operation writing to it is pending or running. Any stale store record that still claims the same device is undocked too (idea#152). Equivalent to a clean physical removal.
- **Usage:** `ejectDisk <diskId>` (the Console sends `disk.id`). A disk name is still accepted for older Consoles and the CLI, under the rules in [Disk arguments](#disk-arguments) (idea#128; eject by id instead). Every refusal ends the command trace as `error` with the reason (idea#152).
- **Scope:** `engine`

### `forgetDisk`
- **Description:** Removes a stale disk record from the shared store (idea#279, idea#282), e.g. the record an older Engine created when it wrote `META.yaml` onto a client SD card. A store edit only: nothing on any disk is read or written. Refused (trace ends as `error`; `error` and `errorMessage` both carry the reason, like other commands) when there is no record with exactly that id (no name fallback, because forgetting cannot be undone), when the record is docked (`dockedTo` or `device` set: eject or unplug it first), or when instance records are still stored on the disk (they would be orphaned; forgetDisk never removes instances). If the disk is an IDEA disk and is plugged in again later, it docks and gets a new record from its `META.yaml` as usual.
- **Usage:** `forgetDisk <diskId> [--with-instances]`, e.g. `forgetDisk 7wt29vdzvj3b2xxt605`
- **`--with-instances` (idea#466):** for a disk that is gone (reflashed, lost), also drops every instance record `storedOn` the disk, in the same store change as the disk record. The disk and instance records are still a store edit only: nothing on any disk is read, written or quarantined, and no container is stopped or removed. After a successful store change, this Engine also prunes unused local Docker networks labelled `com.docker.compose.project=<instanceId>` for each forgotten instance (idea#468). The executing Engine may not be the host where those networks live, so this is local-only: it never prunes on another Engine, never removes the shared `frontend`/`backend` networks, never removes a network that any container still references (running or stopped, e.g. the stopped containers an undock leaves), and does no host-wide sweep. A prune failure is logged and does not fail the command. Allowed only when the disk is undocked on every Engine (no `dockedTo` and no `device` on the record) and none of its instances can have a running container anywhere: the instance status in the shared store (written by whichever Engine runs it) must be `Undocked`, `Docked`, `Stopped`, `Missing` or `Error`. Refusals throw `CODE: text`, end the trace as `error` and leave the store untouched:
  - `NOT_FOUND`: no record with exactly that id (no name fallback).
  - `DOCKED`: the record has `dockedTo` or `device` set (eject or unplug it first; a record left docked by a reused device name is cleared by an Engine restart since idea#465).
  - `INSTANCE_RUNNING`: an instance on the disk is `Running`, `Starting` or `Pauzed` (its containers may still exist).
  - `INSTANCE_STATUS_UNKNOWN`: an instance on the disk has no status or one this Engine does not know, so a running container cannot be ruled out.
  - `BAD_OPTION`: any option other than `--with-instances`.
  - `CHANGED`: the store changed between the check and the removal (re-checked inside the change); nothing removed.

  On success the trace `result` is `{ diskId, diskName, removedInstances: [{ id, name, status }] }`. The local network prune is best-effort and is not part of that result. Without the option `forgetDisk` behaves as before (it refuses while instance records exist). `removeInstance` is not relaxed: it still needs the disk docked to this Engine. Any Engine attached to the store that advertises the capability may run it; the Console does not offer it yet. Example: `forgetDisk updtest10i76 --with-instances`.
- **Scope:** `engine`
- **Capability:** `forgetDisk`; `--with-instances` needs `forgetDiskWithInstances` (idea#466)

### `reboot`
- **Description:** Reboots the engine device.
- **Usage:** `reboot`
- **Scope:** `engine`

## Provisioning Commands

### `buildEngine`
- **Description:** Executes the `build-engine` script to provision a new Raspberry Pi Engine from the current engine. This command streams the output of the build script to the console.
- **Usage:** `buildEngine "--machine <hostname> --user <user> ..."`
- **Scope:** `engine`
- **Note:** The arguments must be passed as a single, quoted string.

### Disk arguments

`installApp` (target and `--source`), `createBackupDisk`, `ejectDisk`, `backupApp` and `restoreApp` (idea#168) take a disk id and resolve it with one shared resolver, `resolveDiskArg` in `src/data/DiskArg.ts` (idea#128):

1. **Id first.** A record with that id must be docked to this engine and have a device. Otherwise the command is refused (`not currently docked`, `not docked to this engine`).
2. **Name fallback (deprecated).** When no record has that id, the argument is matched as a disk name, but only against records docked to this engine with a device. Stale or remote records with the same name are ignored. If two such records share the name, the command is refused as ambiguous and the ids are listed. A name that resolves logs a deprecation warning into the trace: `<command>: disk '<name>' was given by name; use the disk id <id> (names are deprecated, idea#128).`
3. **Not found.** `Disk '<arg>' not found.`

Every refusal throws, so the command trace ends as `error`. The resolver does not refuse the system disk (it is a valid `installApp` target); `ejectDisk` refuses it separately.

A Console can tell whether the Engine takes disk ids from the Engine record: `capabilities.includes('diskIdArgs') && capabilitiesBootedAt === lastBooted` (see ARCHITECTURE.md, Engine capabilities).

A disk name with spaces can be passed as one argument in double quotes, e.g. `restoreApp kolibri "Duration Tests — Add Files App"` (idea#168). A token that starts with `"` runs to the next `"` that ends a token; the quotes are removed. Lines without a `"` are split on spaces exactly as before. Commands that take the whole rest of the line as one argument (`send`, `connect`, `buildEngine`) are not affected; `installApp` takes the rest of the line and splits it with the same quote-aware `splitArgs`.

`createFilesDisk` (idea#131) is new and takes the disk ID only: it uses `lookupDiskById` (the id rule above, without the name fallback). A Console knows the Engine has it when `capabilities.includes('filesDisk') && capabilitiesBootedAt === lastBooted`. Files binds into Apps (`Instance.filesMounts`) need `capabilities.includes('filesMount')` as well (idea#133). Erase needs `capabilities.includes('eraseDisk')` (idea#134). Per-disk allowed actions (`Engine.diskCandidates`, idea#303) need `capabilities.includes('diskCandidates')`; with it, a USB SSD/HDD can be a client-image flash target and `flashCard` returns NOT_REMOVABLE only for a non-USB disk. `flashCard` also writes the Engine's own time zone to the card as `idea-timezone.txt` (idea#208; skipped and logged when the zone is empty or invalid; no new arguments or Console UI).

### Instance arguments

`startInstance`, `runInstance`, `stopInstance`, `copyApp`, `moveApp`, `backupApp` and `restoreApp` resolve their instance argument id-first with `lookupInstanceArg` / `resolveInstanceArg` in `src/data/InstanceArg.ts` (idea#168):

1. **Id.** An instance with that id.
2. **Unique name.** Exactly one instance with that name.
3. **Name on the command's disk.** When several instances share the name, the one stored on the disk the command names: the disk argument of `startInstance` / `runInstance` / `stopInstance` (a disk id or disk name), the source disk of `copyApp` / `moveApp`. A warning in the trace names the id to send instead. This keeps the Console's wire format (`startInstance <name> <storedOn>`, `copyApp <name> <sourceDiskId> <targetDiskId>`) working and unambiguous. `backupApp` / `restoreApp` have no such disk and skip this step.
4. **Refused.** Otherwise the command is refused as ambiguous (the candidate ids and their disks are listed) or as not found. Both refusals end the trace as `error`.

Trace arg keys are unchanged (`instanceName`), so a Console that filters traces by the value it sent keeps working. An Engine with this resolver advertises the `instanceIdArgs` capability (see ARCHITECTURE.md, Engine capabilities); a Console can send instance ids to such Engines.

### Instance data links

`copyApp`, `moveApp` and `installApp` (when it copies an existing source instance) refuse instance data that links off the disk (idea#168 r35). Before anything is stopped or written, the instance folder is scanned; any symlink that resolves outside the instance folder (lexically, or after following the link chain; dangling links included) refuses the command with every such link and its target, e.g. `copyApp: instance data links off the disk: 'data/kolibri' -> '/home/pi/idea166-kolibri-live/data/kolibri'. …`. rsync `-a` and `fs.copy` reproduce a link verbatim, so the copy would share the original's data; the Engine refuses rather than dereferencing, which would silently copy an arbitrarily large external tree. Links that stay inside the instance folder are copied as links. Folders the Engine (pi) cannot read are skipped by this scan; the instance data itself is copied as root by the app-data helper (`idea-app-data copy|send`, idea#168), which keeps owners and modes and runs the same link check as root before it writes anything (`instance data links off the slot: …`). No IDEA product path creates such a link; replace it with the real data and retry.
